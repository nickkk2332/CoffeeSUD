# Generation, loot and random content

This chapter is the guide to everything in CoffeeSUD that builds content from
rules instead of by hand: the MUDPercolator template language (random areas,
rooms, mobs, items, strings, quests), the commands that run it (`GENERATE`,
`GENLAYOUT`, `REGENERATE`, `MPGENERATE`), the seed system that makes a roll
repeatable, loot tables, affixes, name styles, themes and layouts, and how all
of it is saved. It is written for world creators (writing and running template
files), scripters (calling generators from MOBPROG and JavaScript) and engine
developers (the classes behind it). CoffeeSUD keeps the inherited CoffeeMud
generator and adds the G1-G17 features: seeds, preview, depth tags, ENSURE,
MAP and multi-level layouts, FILL, affixes, name styles, REGENERATE, theme
packs and JavaScript in templates. The inherited manual is
[RandomAreas.html](../../CoffeeMud/guides/RandomAreas.html); this chapter is
checked against the parser and supersedes it where they differ (see
[Differences from the old guide](#differences-from-the-old-guide)).

## Concepts

**A template file** is an XML document, normally under `resources/randareas/`
(stock) or `world/resources/randareas/` (your world's own copy, which shadows
the stock file of the same path; see the
[resources overlay](02-world-workflow.md#the-resources-overlay-resources)).
Commands name it relative to `resources/`, for example
`randareas/forest.xml`. The root element is conventionally `<AREADATA>`; the
parser accepts any number of top-level tags, so the root name is only a label.

**A tag** describes something to build. The basic kinds are `AREA`, `ROOM`,
`MOB`, `ITEM` and `STRING`, plus `EXIT`, `AFFECT`, `ABILITY`, `BEHAVIOR`,
`RACE`, `FACTION`, `QUEST`, `OBJECT` and `SCRIPT`. Attribute names are not
case sensitive, and neither are tag names or ids.

**An id** (`id="forest_mobs"`) makes a tag callable: from the `GENERATE`
command, from another tag's `INSERT=`, `LIKE=` or `COPYOF=`, or from a
script. Ids are global to the loaded file set, wherever the tag is nested.

**A container tag** is a tag that holds tags of its own kind (an `ITEM`
containing `ITEM`s, a `STRING` containing `STRING`s). A container usually has a
`SELECT=` rule saying which of its children are used. A tag with no children
of its own kind is a leaf and builds one thing.

**Details.** A built object is filled in from its details: a mob's `NAME`,
`LEVEL`, `RACE`, `DISPLAY` and so on. Each detail is found, in this order, from
a value already defined for the object (`MOB_LEVEL`), an attribute on the tag,
a variable with that bare name, `CONTENT_LOAD`, and finally a child tag of that
name. See [Details given as attributes, tags or variables](#details-given-as-attributes-tags-or-variables).

**Variables** carry context into a build and between its parts. The caller
supplies some (`areaname=Woods`), the layout supplies others (`$roomtag_nodetype`),
and `DEFINE=` and `PREDEFINE=` set more as the build proceeds. A variable that is
an `XMLTag` is evaluated when used, so a `STRING` with an id works as a named
text bank.

**Conditions** (`condition=`) decide whether a tag is an eligible choice;
`validate=` decides, after the tag was chosen, whether it is built at all.
**Requirements** (`requires=`) list variables the caller must supply.

**How a build runs.** For an area: the file is read and its ids registered
(including `LOAD=` and `FROM=` includes and `MERGE=` merges); the requirements
of the AREA are checked; `PREDEFINE`/`DEFINE` are applied; the area is
created and named; its layout manager draws a node graph; the nodes are put
into groups (leaves first, then streets, then everything else) and a room is
built for each by running the AREA's `ROOM` template with that node's
`ROOMTAG_*` variables set; links are joined; `ENSURE` rules run; finally
"post-processing" resolves anything that had to wait until neighbouring rooms
existed (such as `${STAT:ROOM:EAST:MOB:NAME}`). Source:
[MUDPercolator](../../CoffeeMud/com/planet_ink/coffee_mud/Libraries/MUDPercolator.java).

**Entry points.** Everything below ends up in the same library.

| Entry point | Where | Notes |
|---|---|---|
| `GENERATE` | builder command | Builds one thing now, in your room. See [GENERATE](#generate). |
| `GENLAYOUT` | builder command | Draws a layout only. |
| `REGENERATE` | builder command | Rebuilds the area you are in. |
| `MPGENERATE`, `GENSTRING`, `FROMGENFILE` | MOBPROG | Fresh rolls during play. See [Generating in play](#generating-in-play). |
| `gen.item/mob/string/room/area/layout` | JavaScript | Same, from scripts. |
| `StdAutoGenInstance`, `AutoGrid` | area / locale class | Build a dungeon when a party enters. |
| `Prop_LootTable` | property | A loot table on a mob or container. |
| `Regenerate` | area behavior | An area that re-rolls itself. |
| `RandomQuests`, `Prop_QuestGiver` | behavior / property | Generated quests ([quests chapter](08-quests.md)). |

CoffeeSUD removed the inherited network features, but the generator did not
depend on them: everything in this chapter works in the single-player game.
One inherited feature may be inert: `llm="true"` tags are kept only when the
optional LLM integration is installed (see the [LLM attribute](#meta-attributes)).

## Quick start

Always check a file, look at its shape, and preview before building.

```text
GENERATE CHECK randareas/forest.xml
GENLAYOUT TREE 20 SEED=13
GENERATE PREVIEW AREA maze_dungeon FROM randareas/forest.xml areaname=Woods areasize=20 level_range=5 aggrochance=0 theme=forest SEED=13
```

The preview builds the area in memory, lists every room (id, title, node
type, exits, mobs with levels, items), prints the seed, and destroys it. If you
like it:

```text
GENERATE PREVIEW KEEP
```

which runs the real `GENERATE` with the same words and seed, linked nowhere
(unlinked) unless you gave a direction. Link it to your world:

```text
LINK Woods#0 north
```

(from the room it should join; building with `UNLINKED` says the entrance's
room id). To build straight into your world instead:

```text
GENERATE AREA maze_dungeon FROM randareas/forest.xml areaname=Woods areasize=20 level_range=5 aggrochance=0 theme=forest SEED=13 north
```

`GENERATE STRING LIST FROM randareas/forest.xml` lists the ids a file defines
by tag type. The stock `randareas/example.xml` loads all the stock themes and
offers `random_dungeon` (any layout, any theme):

```text
GENERATE AREA random_dungeon areaname=Deep north
```

With no `FROM`, `randareas/example.xml` is used.

## Template file reference

### File structure and includes

A file is a list of tags. A typical themed file (see `forest.xml`) has, in order:

1. a `<STRING id="randomtheme" merge="true">` that adds the theme to the pool
   `random_dungeon` draws from;
2. `<STRING load="/resources/randareas/inc_common.xml" />` lines that pull in
   shared word banks;
3. `AREA` tags (one per layout) that name the layout and the room groups;
4. shared `ROOM` groups (`hallway_rooms`, `interior_rooms`, `leaf_rooms`) that
   several themes each add their own rooms to with `merge="true"`;
5. `MOB`, `ITEM` and `STRING` banks the rooms insert.

To build with it, `GENERATE` reads the file named by `FROM`, registers every
id, then builds the tag whose id you gave. `example.xml` loads every stock
theme so that one `random_dungeon` can choose among them.

Two includes exist and are resolved while ids are registered, before anything
is built:

| Attribute | Meaning |
|---|---|
| `load="path"` | The XML in that file is parsed and added as children of this tag, and its ids are registered. A `condition` on the same tag is tested first; false skips the load. A file is loaded once per run. The path is normally `/resources/randareas/name.xml`. |
| `from="path"` + `id` | This tag must have an `id`. The file is read and the tag with that same id in it is merged into this one (its attributes and children are copied in). Without an `id` the include is refused with a log line. |

Missing files are logged ("Failed loading XML file ..."), and
[GENERATE CHECK](#generate-check) reports them.

### Meta-attributes

These can appear on any tag.

| Attribute | Value | Meaning |
|---|---|---|
| `id` | a name | Registers the tag as callable (case-insensitive). A duplicate id is an error unless both tags have `merge` (see below); the first tag wins and a line is logged. |
| `load`, `from` | path | Includes; see above. |
| `content_load` | path | The text of the file is the value of the tag (variables in it are filled in). Used for long descriptions. A missing file is an error. |
| `like` | ids | Comma list of ids of tags of the *same* kind, not container tags. This tag is built as if it held the listed tags' attributes and children, with its own attributes winning. For one-off variations. |
| `insert` | ids | Comma list of ids of tags of any kind, containers allowed. The wanted kind of tag from each is added as children of this tag, after the inserted tag's own `condition`/`select` ran. `$` before an id is allowed. An unknown id is an error ("Undefined insert"). May instead be an MQL `SELECT:` query ([MQL](#mql-the-query-language)), whose result column named like the wanted tag becomes the choices. |
| `copyof` | id or class | Copies the stats of the tag with that id, or of a prototype class (any mob or item class id, `Cat`, `GenWeapon`), into the object before the tag's own details are applied. |
| `validate` | condition | Tested after a tag was chosen, just before it is built; false skips it silently. For rooms and areas the next candidate is tried instead. |
| `condition` | condition | Tested to decide whether the tag is eligible among its parent's choices. |
| `llm` | `true` | CoffeeSUD keeps this inherited attribute. The tag is dropped when LLM integration is not installed, and when it is, the tag's text is sent to the model as a prompt and replaced by the reply. Stock town and forest descriptions have such lines; without the integration they are silently skipped. |
| `define` | list | Comma list. Applied after the tag is selected. See [DEFINE](#variables-define-and-scope). |
| `predefine` | list | Same syntax, applied whenever the tag is *encountered*, before its choices are considered, whether or not it is later selected. |
| `tagdefine` | list | Same syntax, but the value assigned is the tag itself after `select`/`insert` processing (children replaced by the chosen ones, `select` set to `all`). |
| `select` | mode | How many children to use. See [SELECT modes](#select-modes). |
| `pickweight` | math | Relative weight of this child under a parent using `select="pick-N"`. |
| `merge` | `true`, `false`, `over`, `overN` | Lets two tags with the same id combine. See below. |
| `action` | `append`, `replace`, `prepend` | On a `STRING`-like child: how its value joins the text built so far. The default is append with a space. Anything else is an error. |
| `requires` | list | Variables the caller must define. See below. |
| `seed` | math or word | Seeds the generator for just this `AREA`, `ROOM`, `MOB` or `ITEM`. See [Seeds](#seeds-and-reproducibility). |

**`requires`** is a comma list of `name=type`. Types are `#` (or `number`,
`double`): a number or math expression; `int` (or `integer`): a whole number or
expression; `$` (or `string`): any non-empty text; or a semicolon list of
allowed words (`theme=forest;crypt`). A bare name only demands the variable
exist. `GENERATE` fails with "Required ids for X were missing" and prints what is
needed. Merged tags combine their `requires` (type keywords such as `int` must
agree; allowed-word lists for the same variable are joined with `;`).

**`merge`.** Several theme files each declare `<ROOM id="hallway_rooms"
merge="true">`. When two tags share an id and both carry `merge="true"`: attributes
the first lacks are copied in; `requires` are combined; `condition` and `validate`
are joined with `and`; `insert`, `define` and `predefine` are joined with commas;
any other attribute that differs is logged ("Unable to merge SELECT parm") and the
first wins; the second tag's children are appended, except children marked
`merge="false"` (use that to keep one copy of a child). Tags of different kinds
cannot merge. `merge="over"` makes a tag replace others with its id outright;
`over9` beats `over4`. If a duplicate lacks the merge flag the first tag wins.

**Metacrafted and catalog items.** An `ITEM` or `MOB` `class` can be
`catalog` (with `name`: copy the cataloged object; an item keeps its catalog
cap, see [Loot tables](#loot-tables)). An `ITEM` `class` may also begin
`metacraft:`, to craft a real recipe from the crafting skills:

| `class=` | Result |
|---|---|
| `metacraft:long sword` | The recipe whose name matches. |
| `metacraft:anything` | A random recipe from any crafting skill (the shipwright-type skills are excluded). Tries up to 20 skills. |
| `metacraft:any-blacksmithing` | A random item from one named crafting skill. `any-resources` (or `any-rawmaterials`) gives a random raw resource; `any-farmables` a random farmable. |
| `metacraft:all-<skill>` | Every item of that skill (many items from one tag). `all-resources`, `all-farmables` likewise; `all` alone is every skill. |
| `metacraft` + `name="long sword"` | Same as the first form, naming the recipe in `name`. |

Filters are appended after the recipe: `<` followed by an upper level limit,
`>` a lower level limit, `{` an upper value limit, `}` a lower value limit,
and `=` a class id the item must be an instance of (for example
`metacraft:anything<20{500=GenWeapon`; limits are math). A separate
`material="IRON"` attribute fixes the material. With `class="metacraft:..."` the
level and name still may be overridden by `level=` and `name=`.

### SELECT modes

`select` chooses among the child tags of a container (children of the same
tag kind that fit their own `condition`). `X` below is a number or math
expression (variables allowed).

| Mode | Chooses |
|---|---|
| `all` | Every eligible child. |
| `none` | No child. |
| `first`, `last` | The first or the last. |
| `first-X`, `last-X` | The first X or last X. Error if X is larger than the number of children. |
| `any` | One at random. |
| `any-X` | X different children at random, without repeats. Error if X exceeds the number available, so cover the case where conditions have removed some. |
| `pick-X` | X different children by weight: each child's `pickweight` (math). A child with no `pickweight` weighs 0. If every weight is 0 the choice is uniform; if some are 0 and some not, the 0-weight children are never picked. A negative weight removes the child from the draw. |
| `limit-X` | Up to X at random; fewer is fine, including none. |
| `repeat-X` | X draws *with* replacement: one child may come several times. (The old guide said `repeat` takes every choice; it does not.) |
| a bare number or expression | Treated as `any-X`. |

If there are no eligible children, any mode except `any-0`, `first-0`,
`last-0`, `pick-0` and `limit-X` is an error ("Can't make selection among
NONE"), which stops the build: guard the case with a `condition` on the parent
or choose with `limit`.

What a parent does when it has **no** `select`:

- `AREA` and `ROOM` choices: whatever survives (everything, when there is no
  `select`) forms a pool and *one* of it is picked at random; if its `validate`
  fails, another is tried.
- `MOB`, `ITEM`, `AFFECT`, `ABILITY`, `BEHAVIOR`, `CONTENT`, `FACTION`:
  every eligible child is built.
- `EXIT` choices: one is picked at random for each direction the layout needs.
- `STRING`-valued tags (`NAME`, `TITLE`, `DESCRIPTION`, a `STRING`...): every
  eligible child is joined with spaces, in order. Use `select="any-1"` to pick
  one, and `action` to control the join.

### Conditions and VALIDATE

A condition is a boolean expression evaluated against the current variables.
Everything is compared case-insensitively (the whole expression is upper-cased).

- Variables are written `$name`. An undefined variable is the empty string `''`.
- Constants: numbers; strings in single quotes `'text'` (double quotes and backticks also work).
- Comparison: `=` (also `==`), `!=` (also `<>`), `<`, `>`, `<=`, `>=`.
  Strings and numbers both compare; numeric text compares as a number.
- `x IN y`: true when the string `x` appears inside the string `y`.
- Combining: `AND` / `&&`, `OR` / `||`, `NOT` / `!`, and parentheses.
- A variable may hold a math expression (`1?3`); it is evaluated *once* and the
  result stored, so `$level_range` is stable inside one object.
- A condition can contain an embedded MQL query as a value.
- Math in a condition: `(1?3=1)` is "one chance in three" (see
  [math](#value-substitution)).
- In an XML attribute `<` and `>` must be written `&lt;` and `&gt;`, `&` as
  `&amp;`: `condition="$__boss&lt;1"`.
- `condition="js:expr"` is a JavaScript expression instead
  ([JavaScript in templates](#javascript-in-templates)).

Examples (from the stock files):

```xml
<ROOM condition="$roomtag_isdeepest='true' and $__skeletonboss&lt;1" define="__skeletonboss+=1" ...>
<MOB condition="(1?3=1) and ($pop_mobs!='false')" select="any-1" insert="crypt_mobs" />
<STRING condition="$ROOMTAG_NODEGATEEXIT != ''" action="PREPEND">You are at the entrance. </STRING>
```

`validate` uses the same grammar. The difference: a failed `condition` removes
the tag from the pool *before* `select` counts it (so `select="any-1"` picks among
the survivors); a failed `validate` removes it *after* it was chosen (so you can
end up with nothing). Prefer `condition`.

### Variables, DEFINE and scope

`define`, `predefine` and `tagdefine` take a comma list of items:

| Item | Effect |
|---|---|
| `id` | Sets variable `id` to the value this tag resolves to (its text, or for a tag-valued variable the built tag). |
| `id=value` | Sets `id` to `value` (variables and math inside are evaluated; a pure math expression becomes a whole number). |
| `id+=n`, `id-=n`, `id*=n`, `id/=n` | Reads the variable (undefined or empty counts as 0), applies the operation, stores the result. |

Variable names are stored upper-case. Scope depends on the name:

| Name starts with | Visible to |
|---|---|
| (a letter) | The one room being built (and everything in it). |
| `_` | Every room in the same layout group (a street, a leaf cluster, or the rest). |
| `__` | The whole area. |

So `define="__boss+=1"` with `condition="... and $__boss<1"` hands out one boss
per area. `define` on a nested tag also applies the `define` of its parent if the
parent is the same kind of tag.

Variables the caller passes (`GENERATE ... areaname=Woods`) are "defined" in the
same table. They are *not* the same as MOBPROG variables or saved script
state: they exist for one generation run and are not saved.

### Value substitution

Any text value (a tag's text or an attribute) can contain:

| Form | Meaning |
|---|---|
| `$name` | The variable, case-insensitive; names are letters, digits and `_`. A string beginning with `$` is read as an identifier. If the variable is a tag, the tag is evaluated as a string (`STRING` banks). An unknown variable is an error naming it and the string. |
| `${name}` | The same, with explicit bounds, and optional prefixes: `u:` upper-case, `l:` lower-case, `p:` plural, `c:` capitalised (first letter upper, rest lower), `j:` safe inside JavaScript/MOBPROG (JSON-quoted), `1:` single line, `_:` punctuation removed and spaces to underscores. Prefixes stack: `${c:p:adj_color}`. |
| `$[formula]` | A number from a math formula. |
| `(a(n))` | Removes any article at the start of the following word and puts `a` or `an` according to its first letter. At the very start of a value it also strips articles from the substituted text. |
| `$SYSTEM_RANDOM_NAME:2-4` or `${SYSTEM_RANDOM_NAME:2-4:style:FULL}` | A made-up name of 2 to 4 syllables; see [Name styles](#name-styles). |
| `${STAT:NAME}` | A stat of the object being built (`NAME`, `DISPLAY`, `LEVEL`...). |
| `${STAT:path:...:STATNAME}` | A stat of a *different* object, reached by a path of `ROOM`, `AREA`, a direction (`NORTH`, `EAST`, `UP`...), `ANYROOM` (a random connected room), `MOB` / `ITEM` (a random one in the room), `AREAGATE` (a connected room outside the area). `${STAT:ROOM:EAST:MOB:NAME}` is a mob's name in the room to the east. These wait for post-processing so the neighbouring room exists. |
| `${js:expr}` | What a JavaScript expression gives. |
| `${SELECT: ... }` | The result of an MQL query. |
| `\$` | A literal `$`. |

Math formulas use `+ - * /`, parentheses, and the operators `?` (random
number: `2?5` is a whole number from 2 to 5), `<` (the lesser) and `>` (the
greater), `=` (1 if equal, else 0) and `!` (1 if different). Because `<` and
`>` are operators there, XML writers must still escape them in attributes.

One engine convention to know: every generated text has its apostrophes
turned into backticks (the engine's internal quote; players see apostrophes),
unless `GEN_BACKTICKS=false` in `coffeemud.ini` (see
[Where generated content lives](#where-generated-content-lives)).

### Details given as attributes, tags or variables

Most of an object's fields are "details" (`NAME`, `LEVEL`, `RACE`...). For
each, the generator looks, in this order, and uses the first that exists:

1. a value already defined for this kind of object, `PREFIX_NAME` (for example
   `$mob_level` once the mob's level was set; prefixes `AREA_`, `ROOM_`, `MOB_`,
   `ITEM_`, `EXIT_`, `RACE_`);
2. an attribute on the tag (`level="5"`);
3. a variable of that bare name (`LEVEL` defined by the caller or a `define`);
4. `content_load`;
5. a child tag of that name (`<LEVEL>5</LEVEL>`), which may itself have
   `select`/`condition` children.

So an attribute beats a bare variable beats a child tag. Passing `level=7` on
the `GENERATE` line therefore overrides a `<LEVEL>` child, but not a `level=`
attribute. (The old guide said a defined variable beats attributes; the parser
does the opposite.) Stat codes that do not apply to a class are ignored.

Because detail names *are* the object's stat codes, the attribute list for
`MOB`, `ITEM`, `ROOM`, `EXIT` and `AREA` is the stat-code list of the class you
chose. Lists are given with each tag below. [GENERATE CHECK](#generate-check)
reports attributes that are neither generator attributes nor stat codes of the
tag's class.

| `ROOMTAG_NODEGATEEXIT`, `ROOMTAG_GATEEXITROOM`, `ROOMTAG_GATEEXITCLASS` | gate rooms | Direction of the way out of the area, the room outside, the exit class; with a direction number suffix (`ROOMTAG_NODEGATEEXIT3`) for gates of other directions. |

| `ROOMTITLE_N`... | each room | The title of the neighbouring room that way, if already built. |
| `NODETYPE_N`... | each room | The node type of the neighbour that way. |
| `ROOM_CLASS`, `ROOM_TITLE`, ...; `MOB_NAME`, `MOB_LEVEL`...; `ITEM_NAME`...; `EXIT_*` | building that object | Details as resolved; cleared after the object is built. The plural form (`MOB_NAMES`) accumulates a comma list. |
| `DIRECTION` | building a room | The direction it is placed in. |
| `GEN_SEED` | seeded run | The seed in use. |
| `GAME_DAY` | every run | The global clock's day number (for `seed="$[$GAME_DAY]"`). |
| `PLAYER_LEVEL`, `PARTY_SIZE`, `AREA_LEVEL`, `AREA_THEME`, `HOUR`, `SEASON`, `WEATHER` | `MPGENERATE`, `GENSTRING`, `gen.*`, loot tables | Context of the host. Not set by the `GENERATE` command. |
| `MOB_LEVEL`, `AREA_LEVEL`, `THEME`, `PLAYER_LEVEL` | `Prop_LootTable` | See [Loot tables](#loot-tables). |

Themes define more (`level_range`, `aggrochance`, `theme`, `pop_mobs`,
`pop_items`, `areatype`, `nofantasy`, `multi_level`): these are conventions of
the stock files, not engine variables. `pop_mobs=false` and `pop_items=false`
passed on the `GENERATE` line build an empty shell in every stock theme.

## Tag reference

Each tag below lists what it needs, what it may contain, and its attributes.
"Details" are the stat codes described under
[Details given as attributes, tags or variables](#details-given-as-attributes-tags-or-variables);
any of them may be written as an attribute or a child tag.
Write attribute names in any case. The stat-code lists are those of the
shipped Java classes; the per-class fields of items and mobs are explained in
[Mobs](21-mobs.md) and [Items](22-items.md).

### AREA

Builds an area and all its rooms. Called by `GENERATE AREA`, `MPGENERATE AREA`,
`gen.area`, `StdAutoGenInstance`, `Regenerate`.

**Required details:** `CLASS` (an area class, normally `StdArea`; the stock
themes use `$areatype` if given), `NAME` (must not already exist: building fails
with "you must destroy the old one first"), `LAYOUT` and `SIZE` (rooms; with
`layout="MAP"` the size is the number of rooms drawn and need not be given).

**Optional details** (stat codes of the area class): `DESCRIPTION`, `AUTHOR`,
`CLIMATE`, `THEME`, `BLURBS`, `PREJUDICE`, `BUDGET`, `DEVALRATE`,
`INVRESETRATE`, `IGNOREMASK`, `PRICEMASKS`, `ATMOSPHERE`, `PLAYERLEVEL`,
`PASSIVEMINS`, `CURRENCY`, `TAGS`, `REPUTATION`, `TEXT`, `AFFBEHAV`. See
[Areas](20-areas-rooms-exits.md). Each one is stored in a variable `AREA_<NAME>`.

**Children:** `ROOM` tags (the room templates), `AFFECT` and `BEHAVIOR` tags
(put on the area), `ENSURE` tags, a `MAP` tag and `GLYPH` tags.

**Attributes specific to AREA:**

| Attribute | Meaning |
|---|---|
| `layout` | A layout name, or a comma list (one is picked at random: `layout="MAZE,TREE,CAVE"`). May be a variable. |
| `size` | Rooms to make (math allowed). Also a child tag. |
| `levels` | Number of floors; the size is split over them. See [Multi-level](#multi-level-areas). |
| `levelsdir` | `UP` makes each next floor lie upward; default is `DOWN`. |
| `order` | `depth`, `reverse-depth` or `random`: the order room groups are built in after the entrance. `reverse-depth` builds the deepest groups first so a "one boss" counter is used up at the far end. May be a variable. |
| `mapfile` | Path of a text file with the floor plan for `layout="MAP"`. Resolved under `resources/`, or a path starting `world/` is the world folder. |
| `seed` | Seeds this build. See [Seeds](#seeds-and-reproducibility). |
| `onGenerate` | CoffeeSUD (ST20). Script lines run once, as the area's `GENERATED_PROG`, when the area has been built (`;` stands for a line break), or `LOAD=path` to run a script file. See `GENERATED_PROG` in [triggers](26-mobprog-triggers.md). |
| `requires`, `condition`, `define`, ... | The [meta-attributes](#meta-attributes). |

If a build fails midway, the partial area and its rooms are destroyed.

### ROOM

Builds one room (or, with `layout`, a whole cluster of rooms).

**Required details:** `CLASS` (a locale class: `StdRoom`, `Woods`, `StoneRoom`,
`DarkStoneRoom`, `Road`...), `TITLE` (the room's displayed title; `DISPLAY` is
the stat it fills), `DESCRIPTION`.

**Other details** (locale stat codes): `TEXT`, `AFFBEHAV`, `IMAGE`, `CLIMATE`,
`ATMOSPHERE`, `ROOMID`, `TAGS`, and the physical stats `SENSES`, `DISPOSITION`,
`WEIGHT`, `HEIGHT`, `REJUV`, `LEVEL`, `ABILITY`, `ARMOR`, `DAMAGE`, `ATTACK`,
`AMBIANCES`.

**Children:** `MOB`, `ITEM`, `AFFECT`, `BEHAVIOR` and `EXIT` tags.

**Attributes specific to ROOM:**

| Attribute | Meaning |
|---|---|
| `layout`, `size`, `levels`, `levelsdir` | A ROOM with `layout` builds a *sub-layout*: all `ROOM` tags inside (or inserted) are used to build `size` rooms in that shape, joined to the surrounding layout. Used for a building inside a town. `size` is required. |
| `seed` | Seeds just this room. |

**How rooms are chosen for a layout node.** For each node the AREA's `ROOM`
children are filtered by `condition`, one is picked at random, and if its
`validate` fails another is tried. All the usual nesting works: a group tag
with `insert` and `select`, whose own children carry the `roomtag_nodetype`
conditions (`hallway_rooms`, `interior_rooms`, `leaf_rooms` in the stock files
select rooms for street, interior and leaf nodes).

**Exits.** After the room's contents are made, each direction the layout
joins gets an exit chosen from the room's `EXIT` children; `GENERATE ROOM`
(not part of an area) builds only the exits you ask for with `DIRECTION`.

### EXIT

**Required detail:** `CLASS` (an exit class: `Open`, `GenDoor`...).
**Stat codes:** `NAME`, `DISPLAY`, `DESCRIPTION`, `DOOR`, `LEVEL`, `ABILITY`
(written `MAGICABILITY`), `ISREADABLE`, `READABLETEXT`, `DISPOSITION`, `HASADOOR`, `DEFCLOSED`,
`HASALOCK`, `DEFLOCKED`, `KEYNAME`, `RESETTIME`, `CLOSEWORD`, `OPENWORD`,
`CLOSEDTEXT`, `TAGS`, `AFFBEHAV`. **Children:** `AFFECT`, `BEHAVIOR`.

| Attribute | Meaning |
|---|---|
| `direction` | Limits this exit to one direction (`N`, `E`, `north`...). Only the first letter is compared. |
| `roomlink` | For an exit the layout did not ask for (`$ROOMLINK_REQUIRED` is `false`): the room id of an existing room to link to. |
| a nested `ROOM` | Instead of `roomlink`, a room template to build on the far side of this exit, in this direction. |

An exit with no `direction` is a candidate only for directions the layout
requires. To add extras (a secret door), give `direction` and either
`roomlink` or a nested `ROOM`. A locked door needs a matching key; see
[ENSURE](#guarantees-ensure).

### MOB

**Required detail:** `CLASS`: a mob class (`GenMob`, `GenShopkeeper`,
`GenBanker`...), or `catalog` (then `NAME` is required and names a catalog
mob; a copy is made and counted against its cap).

**Details, stat codes of a generic mob:** `RACE` (a race id, or a `RACE` tag
which may select several), `LEVEL` (a level; at least 1; setting it re-balances
the mob's stats to that level), `GENDER` (first letter used; random M or F
if absent), `NAME`, `DISPLAY`, `DESCRIPTION`, `MONEY`, `VARMONEY`, `ALIGNMENT`,
`DISPOSITION`, `SENSES`, `ARMOR`, `DAMAGE`, `ATTACK`, `SPEED`, `TATTS`
(tattoos), `EXPS`, `IMG`, `FACTIONS`, `TAGS`, and `HPMOD` (the mob class's
`ABILITY` stat; an adjustment to hit points). Character stats by name
(`STRENGTH`, `DEXTERITY`...) and `HITS`, `MANA`, `MOVE`, `HUNGER`,
`THIRST`, `FATIGUE` are also accepted as attributes.
`MOB_POWERBONUS` / `POWERBONUS` makes the mob effectively that many levels
stronger by adding hit points, mana and movement through a `Prop_Adjuster` and
shifting armor, attack, damage and speed.

**Children:** `ITEM` (carried; worn automatically when it can be, unless the
item has `nowear="true"`), `AFFECT` (properties),
`ABILITY` (skills the mob knows), `BEHAVIOR`, `FACTION` (`<FACTION id="..."
value="..."/>` sets a faction value), `SHOPINVENTORY` (for shopkeepers).

A mob is *not* placed by the tag; the room (or `GENERATE`) brings it to life.

### ITEM

**Required detail:** `CLASS`: an item class (`GenItem`, `GenWeapon`,
`GenArmor`, `GenContainer`, `GenFood`, `GenDrink`, `GenKey`...), `catalog` with
`NAME` (a copy of a catalog item; if the catalog entry has a cap and it has been
reached, the tag silently gives nothing), or `metacraft:...` (see
[above](#meta-attributes)).

**Details (stat codes of a generic item):** `NAME`, `DISPLAY`, `DESCRIPTION`,
`SECRET`, `LEVEL`, `USES`, `ABILITY` (written `MAGICABILITY` in a template), `PROPERWORN`, `WORNAND`, `BASEGOLD`
(the item's base value; there is no `value` attribute, see the note below),
`ISREADABLE`, `ISGETTABLE`, `ISDROPPABLE`, `ISREMOVABLE`, `MATERIAL`,
`AFFBEHAV`, `DISPOSITION`, `WEIGHT`, `ARMOR`, `DAMAGE`, `ATTACK`,
`READABLETEXT`, `IMG`, `TAGS`, plus the class's own codes: for a `GenWeapon`
`WEAPONTYPE`, `WEAPONCLASS`, `MINRANGE`, `MAXRANGE`, `AMMOTYPE`,
`AMMOCAPACITY`; for containers `HASLOCK`, `HASLID`, `CAPACITY`, `CONTAINTYPES`,
`DEFCLOSED`, `DEFLOCKED`, `RESETTIME`; for armor `LAYER`, `LAYERATTRIB`; for food
`NOURISHMENT`, `BITE`; for drinks `QUENCHED`, `LIQUIDHELD`, `LIQUIDTYPE`.
**Note:** write the base value as `basegold="75"`. The stock `loot.xml` writes
`value="75"`, which is not a stat code of any item class, so the attribute is
ignored and those items keep their default value. [GENERATE CHECK](#generate-check)
flags such unknown attributes; use it on your own files.

**Children the parser reads:** `CONTENT` (items inside a container), `AFFECT`
and `BEHAVIOR`. (The old guide listed `MOB` and `EXIT` children of an
item; the parser ignores them. An `ITEM` directly inside an `ITEM` does not put
it in the container: it makes the outer tag a selection group. Use `CONTENT`.)

| Attribute | Meaning |
|---|---|
| `nowear` | `true` stops a mob wearing the item automatically. |
| `powerbonus` / `item_powerbonus` | Re-balances the item as if it were that many levels higher (adds protection or damage) but leaves its level. Skipped if the item already has a `Prop_Adjuster`. |
| `affixes` | Math. Rolls that many [affixes](#affixes-and-random-item-properties) onto the item (at most 2: a prefix and a suffix). |
| `modbase` | A modifier base id. Opts the item into tracked, craftable modifiers; see [17-item-modifiers-crafting.md](17-item-modifiers-crafting.md). With `affixes` it also sets how many are rolled. |
| `seed` | Seeds this one item. |

A container item built from a template is closed and locked as its defaults say,
whatever the template did to it afterwards.

### CONTENT

A pure container that holds `ITEM` tags: the contents of a `GenContainer` (see
the riddle chest example in `inc_setpieces.xml`). It may carry `select`,
`condition`, etc., like any container: `<CONTENT><ITEM select="any-3"
insert="dungeon_treasure_items" /></CONTENT>`. Its items are placed inside the
container item.

### SHOPINVENTORY

Inside a shopkeeper `MOB`: the stock. It holds `ITEM`, `MOB` and `ABILITY`
tags (what the shop sells). Either the `SHOPINVENTORY` tag or each of those tags
may carry `number` (stock count, math) and `price` (a value; `-1` is the default
price). If any inventory is generated the shop's existing stock is emptied first.

### AFFECT, ABILITY, BEHAVIOR

**Required:** `CLASS` (an ability id, or a name the engine can find, for
`AFFECT`/`ABILITY`; a behavior id for `BEHAVIOR`). **Optional:** `PARMS`.

- `AFFECT` puts a permanent effect on the thing it is inside: an area, room,
  exit, mob or item (for example `<AFFECT class="Prop_Hidden" />`,
  `<AFFECT class="Prop_OpenPassword" parms="echo" />`). The parameter syntax is
  the property's own: [Properties](23-properties-reference.md).
- `ABILITY` gives a mob a skill it knows (proficiency from `parms`).
- `BEHAVIOR` adds a behavior with `parms`
  ([Behaviors](24-behaviors-and-masks.md)).

Under a `RACE` tag the same tags take extra attributes, `PROFF`, `LEVEL`,
`QUALIFY`; `CULTUREABILITY` is the same as `ABILITY` but for a culture.

### RACE

Used by a mob's `RACE` detail. If `CLASS` names an existing race, that race
is used. Otherwise a new `GenRace` is built from the tag, needing at least five of the
race's stat codes as attributes or children, and **it is added to the engine's race list and
saved through the race store (`DBCreateRace`)**, so it outlives the build.
Because of that, `RACE` tags that build races are best kept to one-time use. Required: `CLASS`, `NAME`.
Optional children: `WEAPON` (holding an `ITEM`: the natural weapon),
`RESOURCES` (items), `OUTFIT` (items), `ABILITY`, `CULTUREABILITY`, `AFFECT`,
`IMMUNITY`. Details are GenRace's stat codes, for example `CAT`, `VWEIGHT`,
`BWEIGHT`, `VHEIGHT`, `FHEIGHT`, `MHEIGHT`, `AVAIL`, `LEAVE`, `ARRIVE`,
`BODYKILL`, `AGING`, `HELP`, `BREATHES`, `HEALTHRACE`, `BODY`, `WEAPONRACE`,
`DISFLAGS`, `EVENTRACE`, `WEAR`, `ESTATS`, `ASTATS`, `CSTATS`, `ASTATE`,
`STARTASTATE`. Races are explained in [Characters](03-characters.md).

### FACTION

`<FACTION id="factionid" value="500" />` inside a `MOB`: sets the mob's value
in that faction ([Society](09-society.md)). Both attributes are required and the
value is a whole number.

### QUEST

Builds a quest *script* (a string), which the quest manager then runs. It is
not an object in the world. Give `QUEST_TEMPLATE_ID` the name of a quest
template (`normal_capture1`) or a path; the template is read from
`resources/quests/templates/NAME.quest`. Every line of its header that starts
with `#$` is a required detail, filled from child tags or variables by the usual
rules; the values are substituted into the script. Optional `DURATION` or
`EXPIRATION` details replace the template's own timing (an `EXPIRATION` quest
is not saved to the database). `generate quest all_quests template=normal
"expiration=20 minutes"` is the stock example, using the documents in
`resources/quests/random/`. The command refuses to continue unless a `QUEST_ID`
variable ended up defined (the quest's name), and refuses a name already in
use. Quest scripts themselves are covered in [Quests](08-quests.md).

### OBJECT

A tag that may hold any mixture of `MOB`, `ITEM`, `AREA`, `ROOM` tags and need
not build anything: if its value begins with `SELECT:` it is an MQL query
that *selects existing objects from the world* instead (and the result carries
their properties). Used mainly by the random quest documents, to pick a real
mob or room as a quest subject. See [MQL](#mql-the-query-language).

### STRING

A text bank. Its value is plain text with substitutions, or children with
`select` and `action`. `GENERATE STRING id` prints one roll. A `STRING` with an
id is also a variable: `$greeting` evaluates it each time it is used.

```xml
<STRING id="museum_greeting" select="any-1">
  <STRING>The bells are silent.</STRING>
  <STRING>A gull circles the tower.</STRING>
</STRING>
```

Within one build, a string variable is evaluated *every time* it is used. To
use the same roll twice, capture it with `define`:
`<STRING id="x" define="whom">$name_bank</STRING>`.

### SCRIPT

`GENERATE SCRIPT id FROM file [vars] target` builds the tag's text as a script and
attaches it to the mob, item or room named by `target`, as a MOBPROG script
host. A `SCRIPT` tag is a string tag whose text is a script (remember that `$n`
style script codes would be taken as variables; escape them with `\$`).

### ENSURE

Child of `AREA`. See [Guarantees: ENSURE](#guarantees-ensure).

### MAP and GLYPH

Children of an `AREA` with `layout="MAP"`. See [MAP layout](#map-layout).

## Layouts

A layout manager draws the shape of an area as a graph of **nodes** (rooms to
be) with links, before any room exists. `layout="..."` on an `AREA` (or a
`ROOM` for a sub-layout) names one. List what is installed:

```text
GENLAYOUT
```

| Layout | Origin | Shape |
|---|---|---|
| `MAZE`, `TREE`, `BRANCH`, `CROSS`, `MESH`, `SPOTTEDMESH` | inherited | Dungeon-style shapes (a maze, a branching tree, a cross, meshes of rooms). |
| `GRIDCITY`, `BOXCITY`, `BOXCITYSQUARE`, `APARTMENT` | inherited | Town-style shapes with streets, blocks and squares. |
| `CAVE` | G16 | Smoothed random blobs and winding passages: a grid filled at random and smoothed, its largest open region grown to the size, each room joined to the one it was reached from and to about a quarter of its other open neighbours. |
| `CLUMP` | G16 | A square block of rooms all joined to their neighbours, with short dead ends off its sides. The entrance is outside it. |
| `LINEAR` | G16 | A road running away from the entrance (two thirds of the rooms) with spurs of one or two rooms off either side. |
| `RING` | G16 | A loop of streets around an open middle, with short spokes in from its sides; for wall walks. The entrance is outside it. |
| `ISLANDS` | G16 | Blobs of rooms in a row running away from the entrance, each joined to the next by a single bridge room. |
| `MAP` | G8 | The plan is drawn by you. See [MAP layout](#map-layout). |

The inherited layouts have no description in the source; draw one with
`GENLAYOUT` to see it. Layout names are case-insensitive. Layouts are
plain classes in `Libraries/layouts/`; an engine developer can add one (the
percolator loads the folder, including the `LIBRARY` path's own `layouts/`
folder).

**Node types** (`$roomtag_nodetype`): `leaf` (one exit: a dead end), `street`
(part of a run of rooms), `square` (a crossing of several), `interior`, and
`surround` (the stock room groups treat it like a street). **Flags**
(`$roomtag_nodeflags`): `corner`, `gate`, `intersection`, `tee`, `offleaf`. **Runs** (`$roomtag_noderun`) for a street: `ns`,
`ew`, `ud`, `nwse`, `nesw`.

**Build order.** Room templates run per node. The first node, the entrance,
becomes room `#0` and is built first. Then **leaf groups** (in a randomised
order), then **street groups** (a straight run of street nodes), then
everything else. A counter such as `__boss<1` therefore fills at the first
matching node built, which is rarely the one you want unless you use the depth
tags or `order`.

**Depth and position tags (G3).** After the layout is drawn, a breadth-first
walk from the entrance sets `$roomtag_depth` (rooms from the entrance),
`$roomtag_depthpct` (0-100), `$roomtag_isdeepest`, `$roomtag_index`,
`$roomtag_x`, `$roomtag_y`, and the area's `$area_maxdepth` and `$area_numrooms`.
Use them instead of build order:

```xml
<ROOM class="StoneRoom" condition="$roomtag_isdeepest='true' and $__boss&lt;1" define="__boss+=1">
  <TITLE>The ogre chieftain's hall</TITLE>
  <DESCRIPTION>Bones and trophies crowd the far wall.</DESCRIPTION>
  <EXIT class="Open" />
  <MOB class="GenMob" level="$level_range + 5" name="the ogre chieftain" display="$mob_name glowers here." />
</ROOM>
```

and let monsters scale: `level="$level_range + $roomtag_depthpct / 10"`.
Add `order="reverse-depth"` on the `AREA` to build the deepest groups before the
shallow ones, so the "one boss" counter is spent at the far end even if your
condition is looser.

### Multi-level areas

`levels="N"` on an `AREA` (or on a `ROOM` with `layout`) draws the layout N
times, once per floor, splitting `size` between them (each floor gets at least 2
nodes), and joins consecutive floors by a stair at a room that is not a leaf
and not the floor's first. Stairs go `DOWN` to the next floor and `UP` back, or
the reverse with `levelsdir="UP"`. Rooms get `$roomtag_level` (1 for the
entrance's floor) and `$roomtag_stairs` (`up`, `down` or `up,down`); the area
gets `$area_levels`. Draw it first: `GENLAYOUT TREE 60 LEVELS=4`.

```xml
<AREA id="goblin_mine" layout="TREE" levels="4" size="60"
      requires="areaname=$,level_range=int"> ... </AREA>
```

### MAP layout

`layout="MAP"` takes a drawn plan: put it in a `MAP` child, or in a file named
by `mapfile=`. Characters:

| Character | Meaning |
|---|---|
| `.` | A street room. |
| `o` | An interior room. |
| `L` | A leaf room. |
| `@` | The entrance (becomes room `#0`). |
| `^`, `v` | Stairs up and down. A `^` is joined to the `v` in the same column on the floor above (the nearest by row). |
| any other character | A room built from the `ROOM` template named by a `<GLYPH char="B" room="boss_room"/>` tag; with no `GLYPH` for it, built from the area's rooms like the others. |
| `-`, `|` | Join two rooms a space apart (east-west, north-south). |
| `+` | Joins like `-`/`|` and makes a door (a `GenDoor`, both ways). |
| `/`, `\` | Join on the diagonal. |
| a line of `=` | Starts the floor above. |
| a space | Nothing. |

Rooms side by side are joined. The size is the number of rooms drawn. Each room
gets `$roomtag_glyph` (the character) and `$roomtag_doors`, besides the
normal tags, so the usual themes dress a drawn plan, and re-rolling changes
text and monsters but keeps the floor plan. A short complete file (adapted from
the G8 fixture):

```xml
<AREADATA>
  <AREA id="abbey" layout="MAP" requires="areaname=$">
    <NAME>$areaname</NAME><CLASS>StdArea</CLASS>
    <MAP>
  L+o-B
    |
    @-^
  =====
      v-o
    </MAP>
    <GLYPH char="B" room="abbey_boss" />
    <ROOM class="StdRoom">
      <TITLE>Abbey $roomtag_nodetype $roomtag_glyph</TITLE>
      <DESCRIPTION>Doors: $roomtag_doors.</DESCRIPTION>
      <EXIT class="Open" />
    </ROOM>
  </AREA>
  <ROOM id="abbey_boss" class="StdRoom">
    <TITLE>The prior's chapel</TITLE><DESCRIPTION>Candles gutter here.</DESCRIPTION>
    <EXIT class="Open" />
  </ROOM>
</AREADATA>
```

A map in a file (`mapfile="world/maps/keep.txt"`) is relative to the world
folder when it begins `world/`, else to `resources/`. Because the room count is
taken from the map, the area needs no `size`.

## Seeds and reproducibility

Without a seed a build uses the game's shared dice and is different each time.
A **seed** makes a build repeatable: the same seed, template files, variables and
engine give the same rooms, text, mobs and items.

**Where a seed comes from:**

| Where | Form |
|---|---|
| `GENERATE ... SEED=n`; `GENERATE FILL ... SEED=n`; `GENERATE PREVIEW ... SEED=n`; `GENLAYOUT ... SEED=n` | A seed for that run. |
| `seed="..."` on an `AREA`, `ROOM`, `MOB` or `ITEM` tag | Seeds just that tag's build. May use variables and math: `seed="$[$GAME_DAY]"` is a dungeon (or boss, or shop stock) of the day. |
| `SEED=` variable of a `StdAutoGenInstance` or `AutoGrid` | A number, `GAME` or `ENTRY`. |
| `MPGENERATE AREA ... SEED=n`; `gen.area(file,id,dir,seed,vars)`; `gen.layout(name,size,seed)` | The same. `MPGENERATE ITEM/MOB/ROOM/QUEST` read a `SEED=` word but do not use it. |
| `REGENERATE AREA SEED=n\|SAME`; `Regenerate SEED=...`; `MPREGENERATE area SEED=...` | See [Fill, regeneration and GENLOCK](#fill-regeneration-and-genlock). |

**Seed values:** a whole number; a math expression (`40+2`); `GAME`, the save's
own seed (made once, kept in the save's header), mixed with the area's name so
each named area differs but each is the same on every visit; `ENTRY`, `RANDOM`
or nothing, a fresh seed (1 to 999999); any other text, a number made from the
text. With no seed given, `GENERATE` picks one and says it:

```text
Seed: 482913 (SEED=482913 builds the same again).
```

**What a seed records.** An area built with a seed carries a blurb flag
`GENSEED n` and, if `GENERATE AREA` built it, a `GENSOURCE` flag. `$GEN_SEED`
(and `${js:defined.gen_seed}`) is the seed inside templates.

**How it works.** A seeded run gives the building thread its own dice stream
started from the seed. Dice rolled by other threads while it runs do not shift
it, and when the run ends the game's own dice carry on as if nothing had been
built (so a preview does not change your next combat). The generator's
post-processing step restarts the stream from a value the seed gives, so it rolls
the same whatever happened in between. Seeded runs also skip the item cache
(`DISABLE=ITEMGENCACHE` does the same globally) and metacrafting takes a fixed
number of tries instead of a time limit; crafted-equipment setup runs on its own
stream so the first build of a seed equals later ones, even in a fresh process
(the `g1-cold` fixture).

**Limits.** The same seed gives the same result only for the same inputs: edit a
template, a recipe set, a name style or the engine and the output changes.
Changing `areaname` changes the text. A tag-level `seed` nests inside the run's
seed and returns to it. `RANDOMSEED=` in `coffeemud.ini` (inherited) seeds the
whole game's dice when the world loads and is unrelated.

**Pattern: keep the dungeon you liked.** Roll `SEED=1` to `20` under
`GENERATE PREVIEW`, keep the best, and write that `SEED=13` into the
`StdAutoGenInstance`'s variables, or into a `Regenerate` behavior with
`SEED=SAME`, so every new game gets that layout.

## JavaScript in templates

CoffeeSUD (G17). `${js:expr}` puts in what a JavaScript expression gives;
`condition="js:expr"` and `validate="js:expr"` keep a tag when the expression is
true. A value that begins `js:` is JavaScript for the whole value.

```xml
<STRING ID="innkeeper_name">${js:require('names').dwarven(2)}</STRING>
<ROOM condition="js:!cm.store('world').bridgeBurnt" ...> <!-- the bridge, until the story burns it -->
<MOB validate="js:defined.level_range &gt; 5 &amp;&amp; test('$theme = crypt')" ...>
```

| Name in the expression | What it is |
|---|---|
| `defined` | The generator's variables, by any case: `defined.level_range`. A number reads as a number; a string tag is filled in first. Setting one (`defined.boss='Grak'`) defines it for what is filled in after; setting it to nothing removes it. |
| `obj` | The object being built (the mob, for its own stats; the room, for its mobs' `validate`), or `null` for a plain string. |
| `test('cond')` | A condition in the template's own grammar: `test('$level_range > 5')`. |
| `cm`, `gen`, `sud` | What every script scope has: `cm.store('world')`, the [generator calls](#generating-in-play), the CoffeeSUD helpers ([JavaScript](05-javascript.md)). |
| `require('name')`, `include(file)`, `debug()` | Libraries from `world/js/lib/` and `resources/js/lib/`. |

Rules and cautions:

- One scope serves a whole build, so a library keeps its state while an area is
  made. `Math.random` is the game's dice, so a seed covers it.
- A text's variables are filled from the last to the first, so a `${js:...}`
  that reads a variable set by a `define` later in the same text sees it.
- Braces inside an expression must pair up. In XML write `&lt;`, `&gt;`, `&amp;`
  for `<`, `>`, `&` in attributes. The generator also keeps `%` in an
  expression as written (`${js:100%20}` is 0, a remainder); put a space after
  a `%` before a hex-looking pair anyway.
- When tags with the same id are merged, their `js:` conditions are joined with
  `&&` (a plain one is wrapped in `test()`).
- An error stops the build with the template, tag and line named (it is also in
  `JS ERRORS`); inside a `condition` an error counts as false.
- `GENERATE CHECK` compiles every `js:` condition and `${js:...}`.
- With `JSCRIPTS=0` in `coffeemud.ini` no template JavaScript runs: `${js:...}`
  gives nothing and `js:` conditions are false. Any other `JSCRIPTS` value lets
  templates run; I found no per-script approval step or time limit in the
  template path (the check is only for `0`).
- Keep expressions cheap and free of blocking calls: they run on the game
  thread during generation.

Do not confuse the two kinds of "variables": template variables
(`defined`, `$name`) live for one build; MOBPROG variables and `cm.store` are
saved game state.

## MQL, the query language

MQL (MUD Query Language) selects, and can change or delete, objects that
already exist in the world, with an SQL-like syntax. In generation it appears in
`OBJECT` tags, `INSERT="SELECT: ..."`, `${SELECT: ...}` values and
conditions (the random quest documents use it to pick real mobs and rooms).
Outside generation it is available as commands and in scripts:

| Where | Syntax |
|---|---|
| `LIST` | `LIST SELECT: ...` (world); `LIST AREA SELECT: ...` (your area only). |
| `MODIFY` | `MODIFY UPDATE: ...` / `MODIFY AREA UPDATE: ...`. |
| `DESTROY` | `DESTROY DELETE: FROM mobs WHERE ...` / `DESTROY AREA DELETE: ...` (previews what it will delete). Needs `CMDAREAS`. |
| MOBPROG | `FOR $1 IN SELECT: * FROM MOBS` loops over a query's rows ([FOR](27-mobprog-commands.md#for)). |

### Statement forms

```text
SELECT: <what> FROM <set> [WHERE <conditions>]
UPDATE: <set> SET <key> = <value> [, <key> = <value> ...] [WHERE <conditions>]
DELETE: FROM <set> [WHERE <conditions>]
```

The colon after the verb is required, and `UPDATE:` names the set directly
(no `FROM`). Keywords are case-insensitive.

**SELECT clause.** Comma-separated terms: a property of the objects in the set
(`NAME`, `CLASS`, `LEVEL`...; unknown properties give an empty string), `*` or
`.` for the object itself, a quoted string or a number, an `$tagname` variable,
or a parenthesised sub-`SELECT:`. `term AS alias` renames a column.
A term may be followed by a narrowing suffix, `\COUNT`, giving how many times
that value appears (`SELECT: name, name\count FROM areas\mobs`). A term may be
prefixed with an aggregate and a backslash: `COUNT\*`, `MEDIAN\level`,
`MEAN\level`, `UNIQUE\name` (and `FIRST`, `ANY` exist in the parser).

**FROM clause.** A *set*: `AREAS`, `AREA` (the area in context), `ROOMS`,
`NPROOMS` (rooms except private property), `MOBS`, `ITEMS`, `PLAYERS`, a CMFS
path to a `.cmare` file (`::/resources/map/plains.cmare`; that is, to inspect
exported content without it being in the world), or a parenthesised
sub-`SELECT:`. In a script the implied set is the scripted object, so on a room
`SELECT: * FROM mobs` is the mobs in that room.

A set may be narrowed with backslash suffixes, each applying to the term before
it: `AREAS`, `ROOMS`, `NPROOMS`, `EXITS`, `MOBS`, `MOB`, `ITEMS`, `ITEM`, `OWNER`,
`FACTIONS` (rows with `ID` and `VALUE`), `PLAYERS`, `PLAYER`, `RESOURCES`,
`NPCS`, `NPC`, `EQUIPMENT`, `ABILITIES`, `PROPERTIES`, `EFFECTS`, `BEHAVIORS`,
and `TAGGED` (objects carrying the tag named by the next term).
The parser also knows `ORPHROOMS`, `RACES`, `SHOP`, `SHOPS`, `SHOPITEMS`.
`SELECT: * FROM AREAS\MOBS\EQUIPMENT` is every worn item of every mob.
Make sure a suffix makes sense for the term before it.

**WHERE clause.** Conditions joined by `AND` / `OR` with parentheses. A
condition is `term comparator term`. Comparators: `=`, `<>` or `!=`, `>`, `<`,
`>=`, `<=`, `IN` (in a set, or a substring), `NOTIN`, `LIKE` (matches a
[zapper mask](24-behaviors-and-masks.md)), `NOTLIKE`, `MATCH` (a regular
expression) and `NOTMATCH`. Narrowing suffixes work in terms.

```text
LIST SELECT: COUNT\* FROM AREAS\MOBS
LIST AREA SELECT: name, level FROM mobs WHERE level > 20 AND name IN 'goblin'
MODIFY AREA UPDATE: mobs SET level = 12 WHERE name = 'a goblin'
```

Check a query with a `LIST` before you `UPDATE` or `DELETE` with it. MQL `UPDATE` and `DELETE` act on live
objects in your area or the world; a touched room is marked unsaved
(`LIST UNSAVED`, `SAVE CHANGED`; see
[World workflow](02-world-workflow.md#unsaved-rooms-undo-and-history)).

## The commands

All of `GENERATE`, `GENLAYOUT` and `REGENERATE` need the `CMDAREAS` security
flag (builders and archons; see
[Configuration and administration](19-configuration-and-administration.md)).
In a normal (non-builder) game a warning reminds you that you are changing the
world.

### GENERATE

```text
GENERATE [NOSAVE] [TYPE] [ID] (FROM [FILE]) ([VAR]=[VALUE] ...) ([DIRECTION]/[TARGET])
GENERATE [TYPE] LIST (FROM [FILE])
GENERATE CHECK [FILE]
GENERATE PREVIEW [TYPE] [ID] ...      GENERATE PREVIEW KEEP
GENERATE FILL [ROOM ID] ...
GENERATE [...] SANDBOX
```

| Part | Meaning |
|---|---|
| `NOSAVE` | Must be the first word after `GENERATE`. Skips the database writes of the new rooms. In CoffeeSUD builder mode this is *not* enough to keep a generated area out of the world files (see [Where generated content lives](#where-generated-content-lives)): use `SANDBOX`, or `DESTROY` the area. |
| `TYPE` | `STRING`, `AREA`, `MOB`, `ROOM`, `ITEM`, `QUEST` or `SCRIPT`. An abbreviation works if it identifies the type by its first letters (`ARE`, `MO`, `ROO`, `IT`, `QU`), but `S` means `SCRIPT` (the last match wins), so spell `STRING`. |
| `ID` | The `id` of the tag (case-insensitive). `LIST` prints every id the file defines, by type. `ALL` builds every tag of that type in the file, one after another (for `AREA` that is one area per id). |
| `FROM file` | Must be the *fourth* word, directly after the id. A path under `resources/` (or the world's overlay). Default `randareas/example.xml`. |
| `VAR=VALUE` | Variables for the build and overrides of any detail. Math is allowed for numbers. Quote a value with spaces: `"areaname=The Old Mine"`. `SEED=` is special (see below). |
| direction | The *last* word, required for `AREA` and `ROOM`. The result is linked to the room you stand in, in that direction. The way must be free ("A room already exists in direction ... Action aborted"). |
| target | The last word for `SCRIPT`: the mob, item or room (in your room) that gets the script. |
| `UNLINKED` | Last word for an `AREA` (before the direction, which may then be omitted): build with no gate, to `LINK` later. The entrance's room id is reported. |
| `SEED=n` | See [Seeds](#seeds-and-reproducibility). Reported when you do not give one. |
| `SANDBOX` | Last word: build in the [sandbox](#sandbox). |

What each type does:

- `STRING` / `SCRIPT`: prints the string (or attaches the script).
- `MOB`, `ITEM`: created in your room ("X appears."), the mob alive.
- `ROOM`: built and linked off your room. In a layout-free `ROOM` template the
  tag's own `EXIT` choices decide the far-side exit.
- `AREA`: built, recorded (`GENSEED` and `GENSOURCE` flags, see
  [regeneration](#fill-regeneration-and-genlock)), added to the world, linked
  (unless `UNLINKED`), and, without `NOSAVE`, written to the database.
- `QUEST`: builds a quest script, creates and starts the quest (refusing if the
  quest has no `QUEST_ID`, no name, or a duplicate name).

Anything you generate with this command also fires `GENERATED_PROG` on the
area or room that was built ([ST20](26-mobprog-triggers.md)).

Examples:

```text
generate area maze_dungeon from randareas/example.xml areasize=50 areaname=test level_range=10?20 aggrochance=50 theme=kobolds south
generate area crypt_dungeon from randareas/crypt.xml areaname=Barrow areasize=30 level_range=10 aggrochance=20 theme=crypt SEED=13 up
generate item goblin from randareas/loot.xml level=4
generate string list
generate quest all_quests template=normal "expiration=20 minutes"
```

Messages worth knowing: "The AREA id 'x' has not been defined in the data
file" (and then the list of ids); "Required ids for x were missing: ..." (name
and type of every variable you still owe); "Unable to fully generate: ..."
(the parser's reason); "Random data file ... not found. Aborting."; "Nothing
generated."

### GENERATE CHECK

```text
GENERATE CHECK randareas/mytheme.xml
```

Loads the file as `GENERATE` would (with `LOAD`/`FROM` includes), builds
nothing, and lists problems as `file:line TAG id: message`:

- what loading logs: duplicate ids, merge conflicts, missing includes, `FROM`
  without an id;
- `INSERT` ids that are not defined; `LIKE` ids not defined or of a different
  tag kind;
- `CLASS` values that are not a class of the tag's kind (catalog and metacraft
  values are exempt);
- unknown `layout` names (each name of a comma list);
- unknown `SELECT` modes;
- `js:` conditions and `${js:...}` that do not compile;
- attributes that are neither generator attributes nor stat codes of the
  tag's class ("unknown attribute");
- variables used but never defined, declared in `REQUIRES`, or created by the
  engine ("variable $x is not defined or declared in REQUIRES");
- `REQUIRES` definitions that cannot be met, and allowed-word lists that merge
  to nothing.

It cannot prove a random combination is reachable, solvable or balanced; see
[Validate the generated game](#validate-the-generated-game). The checks only
look at literal values: anything containing `$`, `(`, `<` or `{` is skipped.

### GENERATE PREVIEW and PREVIEW KEEP

```text
GENERATE PREVIEW [TYPE] [ID] (FROM [FILE]) ([VAR]=[VALUE] ...) (SEED=[N]) ([DIR])
GENERATE PREVIEW KEEP
```

Builds an `AREA` (unlinked), a `ROOM` (in a free direction, or the one given), a
`MOB` or an `ITEM` exactly as `GENERATE` would, with the database left out; lists
the result with its seed; and destroys it. An area listing shows each room's
id, title, node type, exits, mobs with levels and items, with counts; a mob shows
its race, class and gear; an item its level and value. If you gave no seed one is
chosen and printed. `GENERATE PREVIEW KEEP` runs the real `GENERATE` with the same
words and seed (an area unlinked, unless a direction was given) and says
"Kept: ...". The preview is remembered per builder, until the next preview or
`KEEP`.

### GENERATE FILL

```text
GENERATE FILL [ROOM TEMPLATE ID] (FROM [FILE]) ([VAR]=[VALUE] ...) ROOM|AREA (KEEPTEXT) (SEED=[N])
```

Runs a `ROOM` template on rooms that already exist (the room you stand in, or
every room of the area). See [Fill](#generate-fill-on-hand-built-rooms).

### GENLAYOUT

```text
GENLAYOUT [LAYOUT] [SIZE] ([DIRECTION]) (SEED=[N]) (LEVELS=[N])
```

Draws the layout as an ASCII map without building anything: its name and size,
whether all the rooms are joined, a count of each node type, and the map. `O` is
the entrance; other letters are node types and flags. `SEED=n` repeats a
drawing (the seed is printed); `LEVELS=n` draws n floors. `MAP` cannot be
drawn this way (it is drawn in its template). `GENLAYOUT` alone lists layouts.

### REGENERATE

```text
REGENERATE (NOSAVE) AREA ([SEED=N]/[SEED=SAME]) ([VAR]=[VALUE] ...)
REGENERATE LOCK | UNLOCK
REGENERATE
```

Rebuilds the area you are in from its `GENSOURCE`. Details under
[Fill, regeneration and GENLOCK](#fill-regeneration-and-genlock).

### SANDBOX

`SANDBOX ENTER` / `LEAVE` / `CLEAR` / `PREVIEW [name]` and `GENERATE ... SANDBOX`.
The sandbox is a scratch area of four bare rooms in a row, marked unsavable so
neither the world files nor the database ever see it. `GENERATE ... SANDBOX`
adds `NOSAVE`, builds there, and makes any area it builds unsavable too;
`SANDBOX CLEAR` removes the mobs, items and areas generated for it.

## Inspect before committing a dungeon

The routine for any new template:

1. `GENERATE CHECK randareas/name.xml` until it is clean.
2. `GENLAYOUT <layout> <size> SEED=n` a few times to pick a shape.
3. `GENERATE PREVIEW AREA <id> FROM randareas/name.xml <vars> SEED=n` over
   several seeds; read the levels, the mob counts, the boss and key placement.
4. `GENERATE PREVIEW KEEP` for the one you want, then `LINK` it.
5. `WORLD CHECK`, then walk it as a mortal (see
   [Validate the generated game](#validate-the-generated-game)).

A preview of an `AREA` tag needs an *area* template: a bare `STRING` file
cannot be used with it. Remember to supply the template's required variables.

## Generating in play

During play a script can make new things at the moment they are needed. Every
call here is a **fresh roll** (there is no cache), and defines
`PLAYER_LEVEL`, `PARTY_SIZE`, `AREA_LEVEL`, `AREA_THEME`, `HOUR`, `SEASON`,
`WEATHER` and `GAME_DAY` for the template unless you pass your own. The
"player" is the character that triggered the script (if it was a player).

### MPGENERATE

```text
MPGENERATE ITEM  file id [VAR=VALUE ...] [INTO container | TO mob | HERE]
MPGENERATE MOB   file id [VAR=VALUE ...] [HERE | AT room]
MPGENERATE ROOM  file id direction [VAR=VALUE ...]
MPGENERATE AREA  file id direction [VAR=VALUE ...] [SEED=n]
MPGENERATE QUEST file id [VAR=VALUE ...]
```

`$b` is set to the first thing created. Items go into the container, onto the
mob, or on the floor of the host's room (expiring like a monster's equipment).
Mobs are brought to life in the room. A room or area is linked off the host's
room in a *free* direction (an error otherwise), and the area is recorded for
`REGENERATE`. A quest is created and started. The script line is parsed with
the usual `$` substitutions first, so script codes inside values are expanded
before the template sees them. Failures are logged as script errors and the
script continues.

```text
MPGENERATE ITEM randareas/loot.xml chest INTO $i
MPGENERATE MOB randareas/forest.xml forest_faerie_mob level_range=5
MPGENERATE AREA randareas/barrow.xml barrow down areaname=Barrow2 areasize=20 level_range=8 SEED=GAME
```

Reference entry: [MPGENERATE](27-mobprog-commands.md#mpgenerate) and
[MPREGENERATE](27-mobprog-commands.md#mpregenerate).

### GENSTRING and RANDNAME

`GENSTRING(file id [VAR=VALUE ...])` is a function returning the text of a
`STRING` tag; `RANDNAME([style|race|language] [min max] [M|F|N] [FULL])`
returns a random name ([Name styles](#name-styles)).

```text
MPECHO The tavern gossip: $%GENSTRING(randareas/rumors.xml rumor)%
```

(`rumors.xml` is a file you write, with a `<STRING id="rumor">`.)

### FROMGENFILE

The inherited `MPOLOAD`, `MPMLOAD` and friends accept `FROMGENFILE file name
tag [vars]`. It is **cached** by default: the same file, tag and variables give
the same result every time. Add the word `FRESH` for a new roll. Prefer
`MPGENERATE` for new scripts. (Unique "nonce" variables to defeat the cache
leave an entry behind for each value.)

### JavaScript: `gen`

In every JavaScript scope (a `JRUN` script, a MOBPROG `<SCRIPT>` block, a
template's own JS) there is a `gen` object. Results are live objects the script
places or destroys itself. `vars` is a plain object (`{level_range: 5}`).

| Call | Returns |
|---|---|
| `gen.item(file, id, vars)` | An array of items, placed nowhere. |
| `gen.mob(file, id, vars)` | An array of mobs, not yet alive (`bringToLife(room, true)`). |
| `gen.string(file, id, vars)` | Text. |
| `gen.room(file, id, dir)` | A room linked off the host's room in a free direction. |
| `gen.area(file, id, dir, seed, vars)` | An area linked the same way; `seed` a number or `GAME` or `null`. |
| `gen.layout(name, size, seed)` | An array of nodes `{index, x, y, type, exits}` as `GENERATE` would lay out; the same seed gives the same nodes. |

Errors are thrown as exceptions naming the file and id. See
[JavaScript](05-javascript.md).

```js
var charm = gen.item('randareas/loot.xml', 'goblin', {mob_level: 4})[0];
// a cartographer sells a map of the dungeon later made with the same seed
var nodes = gen.layout('TREE', 30, seed);
```

## Autogenerated areas

Two inherited classes build random content as players arrive.

**`StdAutoGenInstance`** (an area class). Each party entering gets its own
fresh copy of the generated area, which lasts until the party has left and
`PASSIVEMINS` have passed. Its two stat codes (editable like any area stat):
`GENERATIONFILEPATH` (the template file, under `resources/`, default root) and
`OTHERVARS` (`NAME=VALUE` pairs, the template's variables). Special variables:

| Variable | Meaning |
|---|---|
| `AREA_ID` / `AREA_IDS` / `AREAID` / `AREAIDS` | The `AREA` tag id, or a comma list to pick from at random. |
| `AREASIZE`, `LEVEL_RANGE`, `AGGROCHANCE`, `THEME` | Template inputs. `StdAutoGenInstance` defaults when absent: size 50, a level range just below the entering player's level, aggro chance equal to their level, a random allowed theme. `AutoGrid` defaults: size from its grid, `LEVEL_RANGE` 1, `AGGROCHANCE` 50 (it logs a warning). |
| `SEED` | A number (the same dungeon each time), `GAME` (the save's own seed, mixed with the area name: the same dungeon every visit in this save) or `ENTRY` (a new seed per entry, saved with the instance). The seed is stored as `GENSEED`. |
| `PASSIVEMINS` | Minutes the instance stays after it empties (default 30). |
| `NORESET` | `true` stops players using the reset-instance trick. |
| `PERSIST` | `true` keeps each group's dungeon, empty or not, until it is reset. |

**`AutoGrid`** (a locale class). A grid locale whose rooms are generated when
someone gets near, using `GENERATIONFILEPATH`/`OTHERVARS` the same way; its
x-by-y size only sets the total room count, since the layout decides the shape.
It takes `SEED` too. Build it as small as you can; generation time is that of any
other random area.

See [Travel, vehicles and instances](30-travel-vehicles-instances.md) for the
instance machinery, and [Areas](20-areas-rooms-exits.md).

## Guarantees: ENSURE

Chance placement ("a key somewhere, one in ten times") can leave a locked
storeroom with no key, or a key behind the door it opens. `ENSURE` (G7) is a
child of an `AREA` that runs after all rooms are laid out and filled, and makes
the area satisfy a rule, repairing it if needed. A rule counts things, then moves
misplaced ones into valid places, then builds fallback copies, then removes
extras.

**Thing rules** (items and mobs):

```xml
<ENSURE name="barrow key" min="1" max="1" fallback="barrow_key"
        where="reachable-without:keyname=barrow vault" in="mob|container" />
<ENSURE var="__torches" min="2" fallback="torch" where="reachable" in="room" />
```

| Attribute | Meaning |
|---|---|
| `name` | Words in the Name of the mobs and items to count (anywhere in the area: on the floor, in containers, carried by mobs). |
| `var` | Instead of names, count by a variable (a counter your `define` increments, such as `__torches`). The final count is stored back in the variable. |
| `min` | At least this many must be in valid places (math). Default 0. |
| `max` | At most this many (only with `name`); extras are destroyed, those in invalid places first. |
| `fallback` | The `id` of an `ITEM` (or `MOB`) tag built to make up the shortfall, repeated until `min` is reached (at most `min*4+4` tries). |
| `where` | `any` (default), `reachable` (from the entrance, through exits), or `reachable-without:keyname=KEY` (from the entrance without passing a door locked with that key name, in either direction). |
| `in` | Where a thing may go: `ROOM` (default), `MOB` (a monster there carries it), `CONTAINER` (a container lying in a room there; a key is never a container); combine with `\|`, commas or spaces. If none of the chosen kinds is available it goes on a room floor. |

The key pattern: the locked room's `EXIT` says `keyname="barrow vault"`, the key
item's `readabletext` is that same text, and the rule above puts the key
only where the entrance can reach it without passing the vault door. An item in
the wrong place is moved before a fallback is built. If there is nowhere at all
the build fails with "nowhere <where> in 'Area' to put X". If `min` cannot be
met a line is logged.

**Room rules:**

```xml
<ENSURE room="barrow_shrine" count="1" replace="barrow_passage" />
```

`room` is the `id` of a `ROOM` tag; the area must contain at least `count`
(default 1) rooms that came from it (a room counts if the template, or any
group tag around it, has that id). If it lacks them, the *deepest* rooms are
emptied (their monsters and items destroyed) and rebuilt from that template,
keeping their exits; `replace` limits which rooms may be taken over to those
built from another template id. The entrance is never replaced.

ENSURE does not prove a scripted puzzle can be solved, only that counts and
reachability hold. A build with a stable `SEED` plus `GENERATE PREVIEW` over many
seeds is how you test it ([g7-ensure fixture](../../tools/fixtures/fixes/g7-ensure.js)).

## Fill, regeneration and GENLOCK

### GENERATE FILL on hand-built rooms

```text
GENERATE FILL forest_rooms FROM randareas/forest.xml level_range=5 AREA
```

You dig the map by hand (`DIG`, `LINK`...), then let a theme write the text,
mobs and items. For each target room (the room you are in, or every room of
the area with `AREA`) the command works out the layout tags the room would have
had, from its *real* exits: `ROOMTAG_NODETYPE` (`leaf` for one exit, `street`
for two, `square` for more), `ROOMTAG_NODERUN` (`ns`, `ew`, `ud`, `nesw`, `nwse`),
`NODEEXITS`, `NODEFLAGS` (`corner`, `tee`, `intersection`, `gate`), the neighbours'
`NODETYPE_x`/`ROOMTITLE_x`/`ROOMLINK_x`, `NODEGATEEXIT` and `GATEEXITROOM` for an
exit out of the area, and the depth tags from a walk from the area's entrance.
It then runs the named `ROOM` template on the existing room: title and
description are rewritten (unless `KEEPTEXT`, or the room is `GENLOCK`), and
mobs, items, effects and behaviors are *added*. **Exits are left alone** and the
room keeps its class. Filling twice adds a second population, so trial it on
a copy. `SEED=n` repeats the fill.

### GENSOURCE and REGENERATE

`GENERATE AREA` records how the area was made in a `GENSOURCE` flag (saved in the
area's `.cmare`): the template file, the `AREA` id, the seed and the variables
you gave. `REGENERATE` reads it:

```text
REGENERATE                      shows how the area was made and which rooms are kept
REGENERATE AREA SEED=SAME       builds it again with the same seed
REGENERATE AREA SEED=77 areasize=30    another seed, and a variable changed
REGENERATE LOCK                 marks this room GENLOCK
REGENERATE UNLOCK
```

Rooms marked **GENLOCK** (the `Prop_GenLock` property,
[reference](23-properties-reference.md#prop_genlock)) are kept exactly as they
are, with their exits: write or change a room by hand, `REGENERATE LOCK` it, and
a better template can be rerun without losing it. The other rooms are replaced
by the new build's rooms of the *same ids*; every exit into the area (the gate
too) is pointed at the room of its id; an exit to a room the new build lacks is
removed; players in a replaced room move to the new room. `NOSAVE` after
`REGENERATE` keeps the database out of it. Without a `GENSOURCE` (the area was
not made by `GENERATE AREA`) it says so.

### Regenerate behavior and MPREGENERATE

For an area that re-rolls itself in play, the
[`Regenerate`](24-behaviors-and-masks.md#regenerate) behavior has
`FILE= ID= VARS="..."` (else it uses the `GENSOURCE`), `SEED=RANDOM|DAILY|WEEKLY|SAME|n`,
`WHEN=MUDDAY:n,MOON:phase,ONEMPTY,SCRIPT` and `KEEP="room ids"`. It never
re-rolls while a player, or someone following one, is inside, and it keeps
GENLOCK rooms, the `KEEP` rooms and rooms a running quest uses. `MPREGENERATE
area|HERE [SEED=n|SAME]` triggers it from a script, and the area's
`GENERATED_PROG` runs afterwards. Define what happens to the monsters and items
the player left behind, and never reroll an occupied mandatory story room without
a designed recovery policy.

```text
GENERATE AREA crypt_dungeon FROM randareas/crypt.xml areaname=Barrow areasize=30 level_range=10 aggrochance=20 theme=crypt SEED=13 UNLINKED
REGENERATE AREA SEED=SAME
```

Worked sequence ("Old Tunnels"): bake the area unlinked, write the story rooms
by hand, `REGENERATE LOCK` each of them, improve the template's descriptions,
then `REGENERATE AREA SEED=SAME`: the hand-written rooms stay and the rest follow
the new template.

## Themes and set pieces

A **theme** is a template file that teaches the generic dungeon structure
how to look and who lives there. The stock themes (loaded by `example.xml` so
`random_dungeon` can roll any) are:

| File | Theme |
|---|---|
| `forest.xml`, `plains.xml`, `snow.xml`, `jungle.xml`, `swamp.xml`, `mountains.xml`, `desert.xml` | Overland terrain. |
| `town.xml` | A town (streets, houses, shops, an inn; adds an `Arrest` behavior). |
| `prison.xml`, `rats.xml`, `lair.xml`, `oceanfloor.xml` | Special-purpose dungeons. |
| `crypt.xml`, `ruins.xml`, `castle.xml`, `volcano.xml`, `sky.xml`, `mine.xml`, `sewer.xml` | G15 themes. |
| `planet.xml` | A root file like `example.xml`: loads the shared banks and several terrain themes. |

Shared banks: `inc_roomruns.xml` (directional wording such as
`$roomexits_desc_long`), `inc_common.xml` (races, metals, woods, junk and
treasure item banks, `dungeon_treasure_items`), `inc_adjectives.xml`,
`inc_dungeonblurbs.xml`, `inc_fantasynames.xml`, `inc_streetnames.xml` and
`inc_setpieces.xml`.

The shared structure is three `ROOM` groups declared with `merge="true"` in
every theme: `hallway_rooms` (street and surround nodes), `interior_rooms`
(square and interior nodes), `leaf_rooms` (dead ends). A theme adds a
`ROOM select="all" condition="$theme='crypt'"` to each, so `$theme` picks which
theme's rooms are eligible. The `AREA` tags (`maze_dungeon`, `grid_dungeon`,
`square_dungeon`, `box_dungeon`, `cross_dungeon`, `tree_dungeon`,
`branch_dungeon`, `spot_dungeon`, each `like=` the first with another layout)
insert those groups.

**Set pieces** (`inc_setpieces.xml`, G15): a theme includes
`<ROOM insert="setpiece_leaf_rooms" />` among its leaves and
`<ROOM insert="setpiece_hall_rooms" />` among its halls. Pieces: a riddle chest
that opens to its answer spoken aloud (`Prop_OpenPassword`), a lever room (a
`Scriptable` on the lever item that opens a cache), a healing shrine, a trapped
corridor (`RandomTraps`), and a collapsed passage with something hidden. Each
comes at most twice an area (the `__setpiece` counter), only two or more rooms from
the entrance (`$roomtag_depth>=2`), and only now and then (`1?4=1`).

**Starting a new theme.** Copy `resources/randareas/theme_skeleton.xml` to
`world/resources/randareas/mytheme.xml`, change every `skeleton` to your theme's
name (it appears once in `requires`, once in the `randomtheme` choice, and in the
ids), and fill its slots: the layout list, the street/inner/dead-end rooms, the
mobs and the boss. Add `<STRING load="/resources/randareas/mytheme.xml" />` to a
copy of `example.xml` (or `load` it from your own root file) and
`random_dungeon` rolls it too. Then:

```text
GENERATE CHECK randareas/mytheme.xml
GENERATE PREVIEW AREA skeleton_dungeon FROM randareas/mytheme.xml areaname=X areasize=30 level_range=10 aggrochance=20 theme=skeleton
```

## Loot tables

`Prop_LootTable` ([reference](23-properties-reference.md#prop_loottable)) gives
a mob or a container a table in a template file, rolled fresh on an event.

```text
Prop_LootTable FILE=randareas/loot.xml ID=goblin ROLLS=0?2 ON=DEATH GOLD=1?10
Prop_LootTable FILE=randareas/loot.xml ID=chest ROLLS=1?3 ON=OPEN
```

| Parameter | Default | Meaning |
|---|---|---|
| `FILE=` | `randareas/loot.xml` | The template file. |
| `ID=` | none (required) | The id of an `ITEM` tag. Without it nothing happens. |
| `ROLLS=` | `1` | How many times the tag is rolled (math: `0?2`). Each roll is fresh. |
| `ON=` | `DEATH` on a mob, `OPEN` on a container | `DEATH`: into the mob's pack as it dies, so its corpse has it. `OPEN`: the first time the container is opened, then not again until its contents reset. `SPAWN`: as the mob is brought to life, or for a container as a player first enters its room. `RESET` is the same as `SPAWN`. |
| `CHANCE=` | `100` | Percent chance that the whole roll happens at all. |
| `GOLD=` | none | Money (math) given as well: to the mob, or placed in the container. |
| `AFFIXES=` | none | Math: rolls that many [affixes](#affixes-and-random-item-properties) onto each item rolled. |

Each roll defines `$mob_level` (the host's level), `$area_level` (the area's
median level), `$theme` (the area's `THEME` blurb flag or theme name, lower
case, `fantasy` if none) and `$player_level` (the killer's or opener's level, or
the host's). Use them in the table: `level="$mob_level"`.

**Writing the table.** An `ITEM` tag with a `select="pick-1"` and `pickweight` on
the choices gives weighted tiers. Nest groups for tiers within tiers. Mix
guaranteed and random entries with `select="all"` at the top. The stock
`resources/randareas/loot.xml` has `goblin` (mostly copper and crude blades, a
war-horn 3%) and `chest` (common 70, uncommon 25, rare 5).

**Container state.** A container rolls once until its contents reset. The state
is `ROLLED=TRUE` kept in the property's own text, which a save keeps. A mob rolls
once per life. A table whose items could not be made (a `MODBASE` item while the
tracked-modifier module is off or its definitions fail `CHECK`) does not count
as a spent roll: the container rolls at its next opening, and a mob's `SPAWN`
roll is made as it dies.

**Catalog caps.** A `class="catalog"` entry copies a catalog item and honours
the catalog's cap and once-ever rules: when the cap of copies in the world is
reached, the entry gives nothing. So a 0.5% entry 'Fang of Grishnak' with a cap
of 1 is the one fang, whoever kills the most goblins. The mob's death-policy
`ITEMLOOTPOLICY` may still ruin an item on its way into the corpse. Verify cap and
once-ever behavior across a save and restore in your own world.

Loot is balanced by *both* the table and any affixes or crafted quality it
composes with: inspect final stats and value, not only the base item.

For a table on a mob made by a template:

```xml
<MOB class="GenMob" level="$level_range" race="Goblin" name="a warren goblin" display="$mob_name snarls here.">
  <AFFECT class="Prop_LootTable" parms="FILE=randareas/loot.xml ID=goblin ROLLS=0?2 ON=DEATH GOLD=1?10" />
</MOB>
```

Related, for random items on a schedule rather than on an event:
[`RandomItems`](24-behaviors-and-masks.md#randomitems) (items from a file,
a catalog list; `AFFIXES=`) and
[`ItemGenerator`](24-behaviors-and-masks.md#itemgenerator) (crafted items weighted
toward the cheap; `ENCHANTED=` percent chance of enchantment).

## Affixes and random item properties

An **affix** is a data-driven random enchantment: a name part and some
properties. An item gets at most one prefix and one suffix that fit its kind and
level, picked by weight.

**Where the data is.** `world/affixes.xml`, else `resources/randareas/affixes.xml`
(or the world's own copy of it in `world/resources/randareas/`). It is read the
first time it is needed and then cached: restart the game after editing it.

**Format.** `<AFFIXES>` holds `<AFFIX>` tags:

```xml
<AFFIXES>
  <AFFIX id="flaming" name="Flaming" pos="prefix" kinds="weapon,ammo"
         level="5-60" pickweight="10" power="2" cursed="false">
    <AFFECT class="Prop_FightSpellCast" parms="10%;Spell_BurningHands" />
  </AFFIX>
  <AFFIX id="bear" name="of the Bear" pos="suffix" kinds="armor,item"
         level="1-60" pickweight="10">
    <AFFECT class="Prop_WearAdjuster" parms="strength+1 hitpoints+10" />
  </AFFIX>
</AFFIXES>
```

| Attribute | Default | Meaning |
|---|---|---|
| `id` | the name, lower-cased | Identifier; one affix is never applied twice to an item. |
| `name` | none (required; an entry without one is skipped) | The word added. |
| `pos` | prefix | `suffix` makes a suffix; anything else is a prefix. |
| `kinds` | `any` | Comma list of `weapon`, `armor`, `ammo`, `item` (anything else), `any`. An ammunition item is `ammo`, a weapon `weapon`, armor `armor`, all else `item`. |
| `level` | `1-9999` | The item levels the affix goes on, `lo-hi` (an item is judged by its base level when the pick is made). |
| `pickweight` | `10` | Relative weight. `0` or less is never picked. |
| `power` | `1` | How much it raises the item's level. Its value rises by `power/10` of the current value (`power="0"` changes neither). |
| `cursed` | `false` | `true` makes the item impossible to take off. |

Each `<AFFECT class=... parms=... />` child adds that property to the item with
those parameters. If the item already has the property, the parameters are
joined (with `;` for a spell-cast property, a space otherwise). `parms` may
instead be the tag's text.

**What an affix does to the item.** The name gets the prefix after its article
(`a short sword` + `Flaming` becomes `a Flaming short sword`; `an` is chosen
when needed) and `of ...` after for a suffix (`of the Bear`; a suffix name that
already starts with `of` is used as is). The room display text follows the new
name. The level goes up by the affix's `power`, the value by a tenth of it each,
the item is marked a bonus item, and a cursed affix makes it unremovable.

**What uses affixes.**

| Use | How |
|---|---|
| `ITEM` template tag | `affixes="0?2"` (math; at most 2 are applied). |
| `Prop_LootTable` | `AFFIXES=1?2`. |
| `RandomItems` behavior | `AFFIXES=...`. |
| `ItemGenerator` behavior, `Thief_Digsite` | Random enchantment (`ENCHANTED=` percent): when affixes exist, an enchanted item gets one affix (a second a quarter of the time); only without an affix file does the old behavior (a plus/minus bump, a curse, or a random spell-cast property; ammunition gets an attack/damage adjuster) apply. |
| `TimsLibrary.enchant` (Java) | The library call behind the last row. |

**Tracked modifiers.** `affix` entries with `tracked="true"` (plus `version`, `tier`,
`group`, `tags` and `<ROLL stat= min= max= />` children; `power` must be 0, no
`cursed`, no `<AFFECT>` children) are the other family. They are chosen only for
items whose template has `modbase="base.id"`, and they save each modifier's
identity, tier, group and rolled values so the item can be crafted on selectively
afterwards. The ordinary affixes above are untouched by them. This is documented in
full in [17-item-modifiers-crafting.md](17-item-modifiers-crafting.md); an item's
`seed` covers its tracked selection and rolls, and instance ids stay distinct.

## Random monsters and other random behaviors

Not everything random needs a whole area. The behaviors below are described in
[24-behaviors-and-masks.md](24-behaviors-and-masks.md); the generator-relevant
facts:

| Behavior | What it does |
|---|---|
| [`RandomMonsters`](24-behaviors-and-masks.md#randommonsters) | Spawns mobs into a room or area every few ticks from a `.cmare` file of mobs, an inline `<MOBS>` block, or `catalog:name,name` (with caps) or `CATALOG="grey wolf=4,dire wolf=1"` with `WHEN`/`DESPAWN`/`NEAR`/`LEVEL`. |
| [`RandomItems`](24-behaviors-and-masks.md#randomitems) | The same for items, including onto mobs; `AFFIXES=`. |
| [`ItemGenerator`](24-behaviors-and-masks.md#itemgenerator) | Items from the crafting skills. |
| [`RandomEncounters`](24-behaviors-and-masks.md#randomencounters) | Encounters from `world/encounters/NAME.enc` as the party moves ([combat and encounters](29-combat-and-encounters.md)). |
| [`RandomTraps`](24-behaviors-and-masks.md#randomtraps) | Traps in rooms/exits/items. Used by the stock `random` theme and the trapped-corridor set piece. |
| [`RandomQuests`](24-behaviors-and-masks.md#randomquests) | Quests from the quest `QUEST` tags; bounded attempts, then it disables itself and logs (G2). |
| [`RandomTeleporter`](24-behaviors-and-masks.md#randomteleporter) | A mob that teleports itself. |

To produce a random *individual* monster with real variation, use a `MOB` tag in
a template with `select`ed `RACE`, `NAME` from a [name style](#name-styles), a
`level` from a range, `AFFECT`s picked with `pick-N`, and equipment from `ITEM`
banks, then call it with `GENERATE MOB`, `MPGENERATE MOB`, `gen.mob`, or from a
`RandomMonsters`-style behavior on a catalog entry.

## Name styles

Random names (G12) are data: one file per style, `world/namegen/STYLE.ini`, else
`resources/namegen/STYLE.ini` (or the world's own copy). Stock styles: `default`,
`elvish`, `dwarvish`, `goblin`. Lines are `KEY=value`; `#` starts a comment; a
key given twice adds to the first.

| Key | Meaning |
|---|---|
| `VOWELS=`, `CONSONANTS=` | The syllables, taken in turn, each followed by a digit of flags: 4 may be in the middle, 2 first, 1 last (7 anywhere, 6 not last, 3 not in the middle). A style without them uses the default's. |
| `START=` | `VOWEL` (the default), `CONSONANT` or `EITHER`: the first syllable. |
| `SYLLABLES=` | `2-4`: how many when the caller asks for none. |
| `PREFIXES=`, `SUFFIXES=` | Comma lists put before or after a made name; `PREFIXPCT=`, `SUFFIXPCT=` (25) their chance. |
| `MALE=`, `FEMALE=`, `NEUTER=` | Given names used `GIVENPCT=` (50) percent of the time instead of a made one. |
| `FAMILY=`, or `FAMILYSTART=` + `FAMILYEND=` | Family names (the full form only). |
| `TITLES=`, `TITLEPCT=` (20) | Titles (the full form only). |
| `RACES=`, `LANGUAGES=` | Races (id, name or category) and languages that use this style. A race's or language's own `NAMESTYLE` (set in its editor) comes first. |

`default.ini` is the old table: replacing it in your world changes every name that
names no style.

**Using a style:**

- In templates: `$SYSTEM_RANDOM_NAME:2-4:elvish` (unbraced) or
  `${SYSTEM_RANDOM_NAME:2-4:elvish}`. The part after the range may be a style, a
  race or a language, and `:FULL` adds the family name and title:
  `${SYSTEM_RANDOM_NAME:2-3:dwarvish:FULL}` gives "Thrain Ironhand the Stout".
  With no style, a `NAMESTYLE` variable the template or its theme defines is
  used, else the mob's race's style. An unknown style is an error.
- In MOBPROG: `RANDNAME([style|race|language] [min max] [M|F|N] [FULL])`
  ([functions](28-mobprog-functions.md#randname)).
- In JavaScript: `CM.core.NameStyles.make(style, min, max, gender, full)`.
- Character creation (`NEW *` at the profile menu) and `Spell_TrueName` offer a
  name in the race's style.

## Where generated content lives

| Situation | What is saved | Where |
|---|---|---|
| Builder mode, `GENERATE AREA ... ` (not sandbox) | The area as ordinary content, with its `GENSEED` and `GENSOURCE` blurb flags. Rooms, exits, mobs, items. | `world/areas/<name>.cmare`, written by `SAVE` or on quit (the exporter writes every live area). |
| Builder mode, `GENERATE ROOM/MOB/ITEM` | Ordinary content in the room it was placed, saved like anything built by hand. | The world files; see `LIST UNSAVED` and `SAVE CHANGED` in [World workflow](02-world-workflow.md#unsaved-rooms-undo-and-history). |
| `GENERATE ... SANDBOX` | Nothing. The sandbox area and areas generated into it are unsavable. | None. |
| `GENERATE PREVIEW` | Nothing. Built and destroyed. | None. |
| A game in play (normal mode), `GENERATE`/`MPGENERATE`/`gen.area`/autogen instances | Areas and rooms made in play are recorded in the save as shapes (a new area's class, name and area data; new, changed and destroyed rooms), the instance children are remade by their parent, and the contents of rooms (mobs, items, doors) are applied on top as for any room. Generated quests are saved whole and made again from their scripts. | The campaign save ([state and persistence](state-and-persistence.md), [saves and party](31-saves-and-party.md)). |
| Seed policy of autogen instances | `GAME` is one seed for the whole save; `ENTRY` creates a seed per instance and saves it. | The save's header / the instance's `GENSEED`. |
| `Regenerate` behavior state | When the days count from, the moon last seen, a re-roll waiting. | Saved with the game as behavior state. |
| `Prop_LootTable` state | `ROLLED=TRUE` in the property text. | With the container. |

Notes:

- `GEN_BACKTICKS` in `coffeemud.ini` (default true): generated apostrophes are
  stored as backticks, the engine's convention. `GEN_BACKTICKS=false` makes
  `GENERATE` (not `MPGENERATE`) keep real apostrophes in what it makes, which
  makes `.cmare` files easier to read.
- `NOSAVE` by itself is not a promise that exports omit a live generated area.
  Use `SANDBOX` for trials.
- Seeded generation and save persistence are separate. A seed lets you rebuild
  an area identically; a save records what *happened* in it. Neither says when a
  cleared dungeon should reset: decide that (`Regenerate`, `ResetWhole`,
  instances) explicitly.
- Use stable ids for content whose discovery must persist across template
  versions.

## Worked examples

The examples are meant to be typed in: each template goes in
`world/resources/randareas/` (your world's overlay; create the folder if it is
not there) and is then named `randareas/<file>` in commands. Run
`GENERATE CHECK` on every file before using it.

### Example 1: a random dungeon area

A burial mound, 24 rooms, a TREE or a CAVE shape picked by the seed, with a
boss at the far end, a locked vault whose key is guaranteed to be reachable,
and undead that get tougher with depth. File
`world/resources/randareas/barrow.xml`:

```xml
<AREADATA>
<STRING load="/resources/randareas/inc_roomruns.xml" />

<AREA id="barrow" layout="TREE,CAVE" order="reverse-depth"
      requires="areaname=$,areasize=int,level_range=int">
  <NAME>$areaname</NAME>
  <SIZE>$areasize</SIZE>
  <CLASS>StdArea</CLASS>
  <DESCRIPTION>Cold passages under a burial mound.</DESCRIPTION>
  <ROOM select="first">
    <!-- the deepest room, once -->
    <ROOM id="barrow_king_hall" class="StoneRoom"
          condition="$roomtag_isdeepest='true' and $__king&lt;1" define="__king+=1">
      <TITLE>the Barrow King's hall</TITLE>
      <DESCRIPTION>Bones and grave goods crowd a stone dais. You can go $roomexits_desc_long.</DESCRIPTION>
      <EXIT class="Open" />
      <MOB insert="barrow_king" />
    </ROOM>
    <!-- one locked vault in a dead end -->
    <ROOM id="barrow_vault" class="StoneRoom"
          condition="$roomtag_nodetype='leaf' and $roomtag_depth&gt;1 and $__vault&lt;1" define="__vault+=1">
      <TITLE>a sealed vault</TITLE>
      <DESCRIPTION>A low chamber behind an iron-banded door.</DESCRIPTION>
      <EXIT class="GenDoor" hasalock="true" deflocked="true" defclosed="true" keyname="barrow vault" />
      <ITEM class="GenContainer" name="a bronze-bound chest" display="A bronze-bound chest sits here."
            haslid="true" defclosed="true">
        <AFFECT class="Prop_LootTable" parms="FILE=randareas/barrow_loot.xml ID=barrow_chest ROLLS=2?4 ON=OPEN" />
      </ITEM>
    </ROOM>
    <!-- everything else -->
    <ROOM id="barrow_passage" class="StoneRoom">
      <TITLE>a cold passage</TITLE>
      <DESCRIPTION>Dust lies thick and undisturbed. You can go $roomexits_desc_long.</DESCRIPTION>
      <EXIT class="Open" />
      <MOB condition="1?3=1" insert="barrow_dead" />
    </ROOM>
  </ROOM>
  <!-- the vault's key: never behind the door it opens -->
  <ENSURE name="barrow vault key" min="1" max="1" fallback="barrow_key"
          where="reachable-without:keyname=barrow vault" in="mob|container" />
</AREA>

<MOB id="barrow_dead" select="any-1">
  <MOB class="GenMob" race="Skeleton" gender="N" level="$level_range + ($roomtag_depthpct / 10)"
       name="a barrow skeleton" display="$mob_name rattles here.">
    <BEHAVIOR class="Aggressive" />
  </MOB>
  <MOB class="GenMob" race="Zombie" gender="N" level="$level_range + ($roomtag_depthpct / 10) + 1"
       name="a barrow zombie" display="$mob_name shambles here.">
    <BEHAVIOR class="Aggressive" />
  </MOB>
</MOB>

<MOB id="barrow_king" class="GenMob" race="Skeleton" gender="M" level="$level_range + 6"
     name="the Barrow King" display="$mob_name sits enthroned here.">
  <BEHAVIOR class="Aggressive" />
  <AFFECT class="Prop_LootTable" parms="FILE=randareas/barrow_loot.xml ID=barrow_king ROLLS=1 ON=DEATH GOLD=60?120" />
</MOB>

<ITEM id="barrow_key" class="GenKey" name="a barrow vault key" readabletext="barrow vault"
      display="A tarnished key lies here." />
</AREADATA>
```

Build it:

```text
GENERATE CHECK randareas/barrow.xml
GENLAYOUT TREE 24 SEED=5
GENERATE PREVIEW AREA barrow FROM randareas/barrow.xml areaname=Barrow areasize=24 level_range=8 SEED=5
GENERATE PREVIEW AREA barrow FROM randareas/barrow.xml areaname=Barrow areasize=24 level_range=8 SEED=6
GENERATE PREVIEW KEEP
```

Read the preview: the boss at the deepest room (`isdeepest`), mob levels rising
with depth, exactly one vault door and one key reachable without it.
`PREVIEW KEEP` builds the last preview unlinked ("`Barrow#0`"); stand where the
tunnel mouth should be and `LINK Barrow#0 down`, then `SAVE`. To regenerate it
with a better description file later: `REGENERATE LOCK` the rooms you edited by
hand and `REGENERATE AREA SEED=SAME`.

Things to notice: the `ROOM select="first"` picks the first eligible template per
node, so ordering is priority. `$__king` and `$__vault` are area counters. A
small area might have no eligible leaf for the vault, in which case the key is
still made (by its `min="1"`); give the area enough rooms (12 or more) or drop
the vault condition's depth test.

### Example 2: a loot table for the boss

File `world/resources/randareas/barrow_loot.xml`. `barrow_king` always drops one
blade with one or two [affixes](#affixes-and-random-item-properties), plus one
extra weighted pick; `barrow_chest` is the vault's three tiers.

```xml
<AREADATA>
<ITEM id="barrow_king" select="all">
  <ITEM class="GenWeapon" level="$mob_level" name="a barrow-iron blade"
        display="A barrow-iron blade lies here." material="IRON"
        weapontype="PIERCING" weaponclass="DAGGER" basegold="300" affixes="1?2" />
  <ITEM select="pick-1">
    <ITEM pickweight="60" class="GenItem" level="$mob_level" name="a string of grave beads"
          display="A string of grave beads lies here." material="GLASS" basegold="40" />
    <ITEM pickweight="30" class="GenItem" level="$mob_level" name="a jade burial mask"
          display="A jade burial mask lies here." material="JADE" basegold="200" />
    <ITEM pickweight="1" class="catalog" name="Crown of the Barrow King" />
  </ITEM>
</ITEM>

<ITEM id="barrow_chest" select="pick-1">
  <ITEM pickweight="70" select="pick-1">
    <ITEM class="GenItem" level="$area_level" name="a coil of rope" display="A coil of rope lies here." material="HEMP" basegold="4" />
    <ITEM class="GenItem" level="$area_level" name="a stub of candle" display="A stub of candle lies here." material="TALLOW" basegold="1" />
  </ITEM>
  <ITEM pickweight="25" class="GenItem" level="$area_level" name="a silver ring"
        display="A silver ring lies here." material="SILVER" basegold="60" />
  <ITEM pickweight="5" class="GenItem" level="$area_level" name="a ruby the size of an egg"
        display="A ruby the size of an egg lies here." material="RUBY" basegold="400" />
</ITEM>
</AREADATA>
```

Attach it as in example 1, with an `<AFFECT class="Prop_LootTable" .../>` in
the mob's or container's template, or add the `Prop_LootTable` property to a
mob you built by hand ([Properties](23-properties-reference.md#prop_loottable)),
and roll the table
without killing anything:

```text
GENERATE ITEM barrow_king FROM randareas/barrow_loot.xml mob_level=10 SEED=3
GENERATE ITEM barrow_king FROM randareas/barrow_loot.xml mob_level=10 SEED=4
```

Each command creates the blade (check its name for affixes) and the extra item
in your room. The last pick (weight 1 of 91) is a catalog item: make the
catalog entry and set its cap with `CATALOG EDIT` first
([Unique and rare items](22-items.md#unique-and-rare-items)), or remove the entry
until you have; a `catalog` entry naming something that is not cataloged is an
error that stops that roll.

### Example 3: a named-item affix set

The Barrow's loot gets a flavour of its own: a set of affixes whose names
tell where the gear came from. Put this in `world/affixes.xml`.
**This file replaces the stock `affixes.xml` completely** (the first file found
is used; they are not merged), so paste back any stock affixes you want to keep
from `resources/randareas/affixes.xml`.

```xml
<AFFIXES>
  <AFFIX id="grave_cold" name="Grave-cold" pos="prefix" kinds="weapon,ammo"
         level="6-40" pickweight="12" power="2">
    <AFFECT class="Prop_FightSpellCast" parms="10%;Spell_Frost" />
  </AFFIX>
  <AFFIX id="barrow_forged" name="Barrow-forged" pos="prefix" kinds="armor"
         level="6-40" pickweight="12">
    <AFFECT class="Prop_WearAdjuster" parms="armor+5" />
  </AFFIX>
  <AFFIX id="last_watch" name="of the Last Watch" pos="suffix" kinds="weapon,armor,item"
         level="10-60" pickweight="6" power="2">
    <AFFECT class="Prop_WearAdjuster" parms="strength+1 hitpoints+10" />
  </AFFIX>
  <AFFIX id="hollow_bones" name="of Hollow Bones" pos="suffix" kinds="weapon,armor"
         level="1-30" pickweight="4" power="0" cursed="true">
    <AFFECT class="Prop_WearAdjuster" parms="attacks-5" />
  </AFFIX>
</AFFIXES>
```

Restart the game (the file is cached after first use), and roll the boss table a
few times, preferably with seeds:

```text
GENERATE ITEM barrow_king FROM randareas/barrow_loot.xml mob_level=12 SEED=1
GENERATE ITEM barrow_king FROM randareas/barrow_loot.xml mob_level=12 SEED=2
```

What you may see: "a Grave-cold barrow-iron blade of the Last Watch" (level
raised by 2 + 2, value by 20% + 20%, a 10% chance to cast Frost on a hit, +1
strength and +10 hit points while wielded), or "a barrow-iron blade of Hollow
Bones" (cursed: it cannot be taken off). The level window matters: at
`mob_level=3` neither `grave_cold` nor `last_watch` can be picked, so the blade
can only get `of Hollow Bones` or nothing. At most one prefix and one suffix are ever applied
(`affixes="1?2"` means "one or two"). A cursed item is dangerous in
play-testing; give it a way out ([Items](22-items.md)).

For affixes that remember what they rolled and can be crafted on later, see
[17-item-modifiers-crafting.md](17-item-modifiers-crafting.md) (`tracked="true"`
affixes and `modbase=`).

### Example 4: a themed village

A small dwarf village with its own naming style, an inn-like hall, a smithy and
homes, in a cross shape: a lane through a green. `world/resources/randareas/stonehollow.xml`:

```xml
<AREADATA>
<STRING load="/resources/randareas/inc_roomruns.xml" />

<AREA id="stonehollow" layout="CROSS" requires="areaname=$,areasize=int,level_range=int">
  <NAME>$areaname</NAME>
  <SIZE>$areasize</SIZE>
  <CLASS>StdArea</CLASS>
  <DESCRIPTION>A dwarf village of low stone halls.</DESCRIPTION>
  <ROOM select="first">
    <ROOM id="sh_smithy" class="StoneRoom"
          condition="$roomtag_nodetype='leaf' and $__smithy&lt;1" define="__smithy+=1">
      <TITLE>the village smithy</TITLE>
      <DESCRIPTION>A forge glows red under a low roof. You can go $roomexits_desc_long.</DESCRIPTION>
      <EXIT class="Open" />
      <MOB class="GenShopkeeper" race="Dwarf" gender="M" level="$level_range + 2" whatisell="inventory only">
        <NAME>Smith ${SYSTEM_RANDOM_NAME:2-3:dwarvish}</NAME>
        <DISPLAY>$mob_name hammers at an anvil.</DISPLAY>
        <BEHAVIOR class="MudChat" parms="" />
        <SHOPINVENTORY number="5">
          <ITEM class="GenWeapon" level="$level_range" name="a dwarven hand-axe"
                display="A dwarven hand-axe lies here." material="IRON"
                weapontype="SLASHING" weaponclass="AXE" basegold="40" />
        </SHOPINVENTORY>
      </MOB>
    </ROOM>
    <ROOM id="sh_home" class="StoneRoom" condition="$roomtag_nodetype='leaf'">
      <TITLE>a dwarf home</TITLE>
      <DESCRIPTION>A snug stone room with a hearth. You can go $roomexits_desc_long.</DESCRIPTION>
      <EXIT class="GenDoor" defclosed="true" />
      <MOB class="GenMob" race="Dwarf" level="$level_range" condition="1?2=1">
        <NAME>${SYSTEM_RANDOM_NAME:2-3:dwarvish:FULL}</NAME>
        <DISPLAY>$mob_name is here, stoking the fire.</DISPLAY>
      </MOB>
    </ROOM>
    <ROOM id="sh_green" class="Road" condition="$roomtag_nodetype='square'">
      <TITLE>the village green</TITLE>
      <DESCRIPTION>A trodden square of grass where the lanes meet. You can go $roomexits_desc_long.</DESCRIPTION>
      <EXIT class="Open" />
    </ROOM>
    <ROOM id="sh_lane" class="Road">
      <TITLE>a stone lane</TITLE>
      <DESCRIPTION>A paved lane between walls of fitted granite. You can go $roomexits_desc_long.</DESCRIPTION>
      <EXIT class="Open" />
    </ROOM>
  </ROOM>
</AREA>
</AREADATA>
```

```text
GENERATE CHECK randareas/stonehollow.xml
GENERATE PREVIEW AREA stonehollow FROM randareas/stonehollow.xml areaname=Stonehollow areasize=14 level_range=6 SEED=2
GENERATE PREVIEW KEEP
```

The style comes from `resources/namegen/dwarvish.ini`
([Name styles](#name-styles)); with `:FULL` a villager gets a family name and
perhaps a title ("Thrain Ironhand the Stout"). To make every dwarf in your world
sound alike, add `RACES=Dwarf` to a world copy of that file (the stock one
already lists it). The `ROOM select="first"` makes the smithy the first leaf, the
homes the remaining leaves, the green the square (if the layout has one; a
`CROSS` has one at the crossing), and lanes everything else. To dress hand-dug
rooms with the same rules instead, use `GENERATE FILL sh_home ... ROOM`.

## Validate the generated game

`GENERATE CHECK` covers class, reference, selector, layout and JavaScript
problems, unknown attributes, undeclared variables and contradictory requirements.
It cannot prove every random combination is reachable, solvable or balanced. A
release checklist for generated content:

1. Run `GENERATE CHECK` on every template you ship and on the ones they load.
2. `GENERATE PREVIEW` over a dozen seeds and a spread of sizes and level ranges.
   Look for empty areas (every `condition` false), missing bosses and keys,
   and absurd mob levels.
3. `WORLD CHECK` the result ([testing and release](13-testing-release.md)).
4. Play it as a mortal: reach the boss, open the vault, loot the chest, die once.
5. Save inside it, restore in a fresh process, and finish it.
6. Check that a failed attempt does not leave orphaned objects or block a
   mandatory quest.
7. For anything that regenerates, test the occupied case, a quest holding a
   room, and a save/restore mid-way.

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `Required ids for X were missing: ...` | The `AREA`/`ROOM` `requires` list a variable you did not pass. Add `name=value` to the command; the message gives the type. |
| `The AREA id 'x' has not been defined in the data file.` | Wrong id or wrong `FROM`; run `GENERATE AREA LIST FROM file`. Remember `FROM` must come right after the id. |
| `When creating an area or room, the LAST parameter to this command must be a direction` | Add a direction as the very last word (or `UNLINKED` for an area). |
| `A room already exists in direction ...` | The way is taken; choose a free direction or `UNLINK` first. |
| `Unable to create area 'X', you must destroy the old one first.` | An area of that name exists. Change `areaname`, or `DESTROY AREA`. |
| `Can't make selection among NONE` / `Can't pick N of M` | A `select` found fewer eligible children than it needs. Use `limit-N`, or make the conditions total. |
| `Unknown variable '$x'` | Undefined variable in a value. Declare it in `requires`, `define` it, or fix the spelling (`GENERATE CHECK` finds these). |
| `Undefined insert: 'x'` | `insert=` names an id that is not loaded. Check the `load=` and the id's spelling. |
| `Duplicate ID` in the log | Two tags share an id without `merge="true"` on both. |
| A detail has no effect | It is not a stat code of that class (for example `value` on an item; use `basegold`). `GENERATE CHECK` reports "unknown attribute". |
| A condition is never true | `<` and `>` unescaped (XML would reject the file), a string compared without quotes, or a variable that is a math expression (`1?3`) compared as text. Turn on `DEBUG=MUDPERCOLATOR` (with `DBGMSGS`) in `coffeemud.ini` for a trace of every condition test and define. |
| Same seed, different dungeon | A different template, recipe set, name style, variable or engine version; a changed `areaname` changes text. Check `GEN_SEED` and the `GENSEED` area flag. |
| `${js:...}` gives nothing | `JSCRIPTS=0`. Or an error: `JS ERRORS`. |
| Loot never appears from a container | It already rolled (`ROLLED=TRUE`) and its contents have not reset; or `CHANCE` failed; or the item is a capped catalog entry at its cap. |
| Boss is next to the entrance | You relied on build order. Use `$roomtag_isdeepest`/`depthpct` and `order="reverse-depth"`. |
| `REGENERATE` says there is no GENSOURCE | The area was not made by `GENERATE AREA` (or the flag was cleared). Use `Regenerate` with `FILE=`/`ID=`. |
| New area saved into `world/areas` after a "trial" | `NOSAVE` does not keep builder-mode exports out. Use `SANDBOX` or `GENERATE PREVIEW`, or `DESTROY AREA` before saving. |
| A theme loads but never appears in `random_dungeon` | Its `randomtheme` choice or its `random_dungeon` `insert` is missing, or its `theme` value does not match the theme tests in the room groups. |

## Differences from the old guide

For readers who know `guides/RandomAreas.html`:

- `select="repeat-X"` draws X times *with replacement*; it does not select every
  choice.
- A detail given as an attribute beats a variable of the same name, which beats a
  child tag (the guide said the variable beats both).
- `BRANCH`, `MESH` and `SPOTTEDMESH` layouts exist; the guide's list is
  incomplete. `CAVE`, `CLUMP`, `LINEAR`, `RING`, `ISLANDS` and `MAP` are
  CoffeeSUD's.
- An `ITEM` has no `MOB`/`EXIT` children in the parser; items inside items are
  groups, not container contents (use `CONTENT`).
- There is no `value` attribute for items (it is `basegold`).
- `NOSAVE` does not prevent a builder-mode export of the area.
- Template JavaScript is not subject to the per-script approval list (see
  [JavaScript in templates](#javascript-in-templates)).
- GENERATE accepts the types `STRING`, `AREA`, `MOB`, `ROOM`, `ITEM`, `QUEST` and
  `SCRIPT`; the guide omitted `SCRIPT`.
